# Code Review and Quality

基于 Addy Osmani 的五维审查方法进行项目适配。目标是确认本次改动提高整体代码健康度；结论由真实调用链、契约与验证证据支撑，零问题是有效结果。

[代码审查规范](../../../docs/agent/代码审查规范.md) 是风险分级、门禁、P0/P1/P2 和报告格式的唯一真源；按需读取对应章节。工程职责以 [AGENTS.md](../../../AGENTS.md) 为准。本技能补充审查视角，不建立第二套门禁或要求每次小改动进行全量审计。

## 范围和证据

- 先明确需求、预期行为、比较基线和本次实际修改文件；共享工作区的 Git/SVN 状态不能直接当作本轮白名单。
- 有 CodeGraph 索引时，先查询目标符号和调用链；源码缺失或过期再定向读取。检查测试意图与真实实现，核对调用方、上游校验和下游消费者后再报告问题。
- 区分已有缺陷与本次引入的回归。工程已有红灯时遵守相对基线零新增的口径，不要求靠修改基线、删测试或扩大任务范围获得全绿。

## 五个审查维度

| 维度 | 本项目重点 |
| --- | --- |
| 正确性 | 需求与协议是否一致；边界、错误、取消、重开会话和重复请求是否保持不变量；测试是否 import 真实实现并能观察目标行为 |
| 可读性与简单性 | 是否复用既有类型和工具；包装层是否有价值；分支是否表达真实业务；重构是否减少理解负担，而非只移动复杂度 |
| 架构 | MVC、依赖方向、组合层和资源归属是否正确；feature 规则是否泄漏到通用模块；是否引入平行状态机或重复真源 |
| 安全 | 外部协议/配置是否在边界校验；凭据是否进入代码或日志；外部文本是否被误当指令；本次依赖变更的来源、许可证及已知风险是否核实 |
| 性能 | update/render 热路径是否新增分配、全局配置查询、资源加载或无界工作；是否破坏幂等渲染和既有节流；性能结论有无对应测量 |

按真实场景选检查项。REST 分页、SQL、Web DOM 重渲染等上游例子不自动成为 Cocos 客户端要求；文件行数、改动行数、抽象使用次数只可作为检查线索，不作为硬门槛。

## 结构问题如何判断

提出结构建议时，指出具体复杂度来源、受影响调用方及能减少负担的最小调整：复用已有规则、移回功能所属层、明确类型或移除确无职责的包装。保留协议适配、依赖隔离和生命周期管理的必要间接层。

有充分证据表明本次结构变差才按项目规范升级严重度；个人偏好不能变成阻断项。修复建议须保留校验、错误处理、取消与释放。仅发现历史债务时单独记录，不顺带要求重构无关模块。

审查请求默认只读。需要验证“测试是否真能捕获错误”时，先检查断言与行为关系；确有必要的临时变异验证放在隔离副本中，不改动共享脏工作区再整体恢复。没有做过实验就说明验证边界。

## 验证与交付

- 复用 [规范路由与最小验证](../../../docs/agent/规范路由与最小验证.md) 的绑定测试和现有 verify 工具；只运行本次相关检查，跨模块/公共契约按工程规则扩展。
- 核对实际命令、退出码、失败用例/错误指纹和基线；区分已验证、静态推断和未覆盖。没有运行测试就不能写通过。
- 依项目审查格式，先给总体结论及关键风险，再按 P0/P1/P2 一轮列全问题。每项给出准确文件行、触发条件、影响、证据及最小建议；既有问题与新增问题分开标注。
- 无问题时说明检查范围、证据和剩余边界，不制造 Nit 或为了凑维度写无效建议。
- 默认单 Agent。同行评审要求遵守项目风险规则；不自动切换模型或启动代理，不创建 CI、hook，不提交、推送或发消息。

例如，新增请求的成功路径测试通过，但退出时没有解除真实 caller，属于需追踪取消与回调归属的正确性/架构问题；旧基线的一条无关失败应单列，不据此断言该请求回归。
