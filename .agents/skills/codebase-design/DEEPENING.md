# 依赖与模块接口

当接口复杂度来自依赖组织方式时使用本参考；沿用 [技能入口](SKILL.md) 的职责与范围。

## 先判断依赖类型

| 依赖 | 如何评估与验证 |
| --- | --- |
| 进程内纯计算或状态 | 把规则集中在其拥有者，通过真实函数和不变量测试验证；纯计算并不自动意味着应合并模块 |
| 可本地替换的 I/O | 复用已有 repository/gateway、fixture 和测试替身，验证公开契约；不为本次设计另造依赖系统 |
| 自有远程服务 | 明确协议、失败、未知结果和取消契约，注入已有端口；服务端规则不能由客户端单侧修改 |
| 外部服务 | 在现有 adapter 边界校验和归一化；替身测试覆盖已确认的契约，不能据此声称真实集成通过 |

## 接口与职责

- “更深”表示接口给调用方提供更多有用行为、更少实现细节；不表示类更大、文件更少或 MVC 层合并。
- 复用已有注入端口。新增端口应有本次需求中的实际隔离、生命周期或测试收益，不以实现数量机械判断。
- 不把内部可替换点全部公开；优先用现有公开接口表达可观察结果。
- 规则与状态归 Model，外部数据归 Repository/Gateway，Controller 管理交互和在途操作。接口调整需保留这些归属及错误、取消、释放语义。

## 测试迁移

只有在被测契约已迁移、替代测试覆盖原有行为，并核实无其他用途后，才移除确实失效或重复的旧测试。新的接口行为测试不能替代分层守卫、真实 caller 解除、重开会话和生命周期回归。

测试若必须随内部重构修改，先区分它是在约束业务行为，还是在守护工程结构；结构测试本来就可以约束实现边界。
