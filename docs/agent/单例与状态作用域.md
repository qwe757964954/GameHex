# 单例与状态作用域

单例是表达“在某个生命周期内只有一个共享实例”的实现方式，本工程不全面禁用单例。选择依据是唯一性、状态归属与生命周期，而不是类名或 instance/static 写法。通用分层及 MVC 仍见[工程入口](../../AGENTS.md)和[MVC 设计规范](MVC设计规范.md)。

## 1. 何时适用

| 场景 | 处理方式 |
| --- | --- |
| 游戏运行期唯一的事件、弹窗、音频等公共服务 | 可以单例，优先复用已有入口，明确初始化宿主 |
| 当前账号或会话共享的缓存、连接、会话服务 | 可以在账号/会话作用域内唯一；明确切账号、退出登录及重连时的重置策略 |
| 页面、弹窗、每局战斗或每个实体的数据 | 默认由对应宿主持有实例；“当前只开一个”不等于全局生命周期；确有共享需求时先说明作用域 |
| 纯计算、常量、配置快照 | 优先纯函数/不可变数据，不为访问方便添加持有可变状态的单例 |
| 跨流程临时传参 | 优先 entry params / context；必要桥接明确消费者，单次消费、读取即清空 |

账号共享状态可以由会话服务管理，不要求把其中所有对象都改成全局实例。公共服务持有可变状态并非天然违规，重点是状态有明确归属、隔离和重置方式。

## 2. 新增或调整时说明什么

- 为什么需要唯一实例，其作用域是应用、账号、会话还是场景；哪个已有宿主负责初始化。
- 谁可以访问，依赖是否符合分层；不要将任意 Service.getInstance 当成绕过端口或组合层的通道。
- 必要的 reset/dispose/退订由谁调用，如何处理退出、切账号、场景切换与迟到异步结果。无需给确实与应用同寿命且无待清理状态的对象机械增加空释放方法。
- 可变状态相关测试如何独立运行：优先注入实例/端口，必要时使用既有 reset/测试装配，避免前一测试污染下一测试。

这些说明放在相关契约、代码设计或变更说明中即可，不要求逐次申请“允许单例”。复用既有公共单例入口时不重复论证、不顺手改造稳定实现。

## 3. 仍需遵守的边界

- core 保持纯 TS，不直接创建/获取运行期全局服务，不直接 I/O；需要的依赖经参数或端口传入。此限制针对 core，不扩大为整个工程禁用单例。
- Controller/Composition 可以按既有约定使用获准的公共服务。View 仍只持有展示契约、派发意图，不因服务是单例就直接扣费、请求业务接口或控制流程。
- 单例不替代 ControllerBase/PopupBase/ResourceScope 的资源管理，也不代替页面/对局/账号的状态归属。
- 禁止无宿主、无清理策略的全局/static 业务暂存；不得通过把全局变量包进单例类来规避该约束。static 常量或无状态方法不等同于业务状态暂存。
- EventMgr.instance / CacheMgr.instance / PopupManager.inst 等必需入口沿用非空契约；真正可选的服务/查询结果才表达为空，不为所有单例统一添加静默兜底。

## 4. 最小验证

改动涉及哪个生命周期，就验证对应的初始化、切换或释放；可变账号/对局状态验证隔离与重置，带订阅/请求的服务验证解除后迟到结果不污染新宿主。运行相关既有测试集，不因采用单例就要求全仓测试或新建另一套容器。
