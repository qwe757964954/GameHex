# 测试基线红清单

> 用途：让「本来就有哪些用例是红的」有归属，而不是躺在 `tmp/verify/baseline.json` 里当匿名数字。

## 为什么有这份清单

`tmp/verify/baseline.json` 是「相对基线零新增」判据的快照，但它只有一个**扁平的名字数组**：
97 条红没有 owner、没有归属域、没有「是不是真红」。后果有两个：

1. 红挂着没人认领，「新增 0」成了唯一有人看的数字，其余被无视；
2. **重算基线时一次性把新红吞进快照** —— 回归从此不可见，还没人知道发生过。

2026-11-13 给 `tools/verify/verify.mjs` 加了两道约束：

- `baseline` 模式在「新增失败 / 新增 tsc」时**拒绝写盘**，必须 `VERIFY_BASELINE_ACCEPT=1` 才覆盖；
- 覆盖时追加 `tmp/verify/baseline-accept.log`：谁、什么时候、把哪些红写进了快照、口径从多少变到多少。

## 「单跑复核」这一列怎么读

全量是 60 文件一批跑的。批次超时或资源竞争会让**整个文件**报 `not ok <文件路径>`（不是某条断言失败），
单跑该文件却全绿 —— 这类是**采集噪声**，改代码只会改坏东西。

2026-11-13 实测：`battle-runtime-controller.test.ts` 在批跑里报文件级红，单跑 26/26 全绿。
所以清单把两者分开：`单跑也红（真红）` 才需要改；`单跑绿（批跑噪声）` 重跑一次通常就消失。

## 重算基线的正确姿势

1. 按清单把`真红`修掉，或确认某条属于「已接受」并写下理由；
2. `npm run verify:baseline` —— 若还有新增，守护会**拒绝**并列出差异；
3. 确需带红入库：`VERIFY_BASELINE_ACCEPT=1 npm run verify:baseline`，然后检查
   `tmp/verify/baseline-accept.log` 是否记录完整；
4. 重算后跑一次 `node tools/verify/verify.mjs reds`，刷新本文件的表格。
