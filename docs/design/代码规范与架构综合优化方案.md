## 一、Lambda 与闭包优化方案

### 1. 现状痛点
- **高频循环与帧驱动中分配内联 Lambda**：在 `update(dt)`、`step(dt)`、ECS 系统遍历或高频事件循环中，使用 `array.filter(x => ...).map(y => ...)` 或动态创建闭包。每次调用均在堆上分配新的函数对象与作用域链，加剧 V8 / JSC 的 Minor GC 频率，在移动端（尤其是低端安卓机与小游戏环境）导致周期性微卡顿与掉帧。
- **事件与网络订阅使用匿名 Lambda 导致无法精确退订**：使用 `EventMgr.instance.on(event, (e) => this.handle(e))`，未绑定真实宿主 `caller`，导致页面销毁时无法通过 `offTarget(this)` 统一释放，形成隐蔽的内存泄漏与孤儿回调。
- **异步链路中闭包捕获大对象导致宿主驻留**：Promise 链式调用或 `scheduleOnce` 捕获整个 `this`，当节点已销毁或页面已关闭时，未落定的闭包依然持有该引用，阻碍垃圾回收并可能引发空指针报错。
- **简单转发的过度包装**：形如 `onClick: () => this.close()` 的无意义箭头包装，徒增调用栈层级。

### 2. 治理规约与重构模式

#### 规约 1：热路径与帧更新零内联 Lambda 分配
- **标准**：在 `update`、`step`、物理/动画逐帧计算与高频消息流中，严禁在循环内分配箭头函数。
- **模式**：
  ```ts
  // 🔴 错误：每帧创建闭包与临时数组，触发 GC
  update(dt: number): void {
      this.activeItems.filter(item => item.alive).forEach(item => item.step(dt));
  }

  // 🟢 正确：原生索引循环，复用预声明方法或就地处理，零堆分配
  update(dt: number): void {
      const items = this.activeItems;
      for (let i = items.length - 1; i >= 0; i--) {
          const item = items[i];
          if (!item.alive) {
              items.splice(i, 1);
              continue;
          }
          item.step(dt);
      }
  }
  ```

#### 规约 2：事件与网络监听必须传递真实宿主 Caller
- **标准**：事件中心与网络协议订阅必须传递具体方法引用与宿主 `this`，退订时一次性解除全部绑定。
- **模式**：
  ```ts
  // 🔴 错误：无法精确 off，容易遗留孤儿监听
  EventMgr.instance.on(TerritoryUiEvent.Intent, (e) => this.onIntent(e));

  // 🟢 正确：显式传递 caller 与方法引用，退出时统一释放
  EventMgr.instance.on(TerritoryUiEvent.Intent, this.onIntent, this);
  // 销毁时统一收口：
  EventMgr.instance.offTarget(this);
  ```

#### 规约 3：异步闭包的作用域隔离与取消守卫
- **标准**：异步链中若捕获外部标识，优先仅捕获基础类型 ID；`await` 之后必须包含宿主有效性与竞态校验。
- **模式**：
  ```ts
  async doAsyncWork(cellId: number): Promise<void> {
      const loadId = this.loadId;
      const requestId = ++this.interactionId;
      const result = await this.service.fetchData(cellId);
      // 必须校验宿主与竞态有效性
      if (!this.isValid || this.loadId !== loadId || this.interactionId !== requestId) {
          return;
      }
      this.applyResult(result);
  }
  ```

## 二、注释体系优化方案

### 1. 现状痛点
- **注释充当“需求变更日志”**：代码中大量残留 `// 2026-10-xx 用户提出改成...`、`// 第 14 批需求口径...`。阅读者需要耗费巨大心智解析早已过期的需求历史，无法直接看清当前生产代码的真实契约。
- **大段废弃代码被注释保留**：被淘汰的方案 1、旧计算公式整块注释留在文件中，造成文件膨胀与搜索污染。
- **复述代码的无意义废话**：如 `// 设置位置` 下面紧接 `setPosition(...)`。
- **关键设计“Why”与数学几何不变式缺失**：缺乏对 2.5D 台面偏移、Sprite Trim 补偿、着色器 uniform 顺序、并发锁等非直觉机制的解释。

### 2. 治理规约：“三不写、三必写”原则

```
┌─────────────────────────────────────────────────────────────┐
│                      注释治理核心原则                       │
├──────────────────────────────┬──────────────────────────────┤
│           三 不 写           │           三 必 写           │
├──────────────────────────────┼──────────────────────────────┤
│ 1. 不写代码字面行为复述     │ 1. 必写业务原因与「Why」     │
│ 2. 不在代码中堆砌变更日志/对话│ 2. 必写引擎/平台物理与时序陷阱│
│ 3. 不留被废弃的整块注释代码  │ 3. 必写数学几何不变式与删除条件│
└──────────────────────────────┴──────────────────────────────┘
```

#### 规约 1：三不写（清除噪音）
1. **不写需求变更史与时点日记**：将“第 N 批”、“用户在某天要求”剥离至 Git Commit 日志或 `docs/` 规范文档；代码注释只解释「当前规则是什么」，不记录「过去怎样试错」。
2. **不留废弃代码块**：已废弃的代码直接删除，依托 Git / SVN 版本库追溯历史。
3. **不复述代码字面逻辑**：禁止出现 `// 获取按钮`、`// 赋值变量` 这一类低价值注释。

#### 规约 2：三必写（沉淀高价值契约）
1. **必写业务原因（Why）**：解释非直觉的业务决策。例如：为什么该协议必须“只发不等”、为什么某一格未配置关卡时按钮置灰而不是隐藏。
2. **必写引擎机制与时序陷阱**：例如 Sprite Trim 影响渲染包围盒、Label 强制在同帧 `updateRenderData(true)` 刷新排版的物理原因、Prefab 节点层级重排（reparent）对点击区域的影响。
3. **必写数学几何不变式与删除条件**：例如六边形格心台面抬升量 `HEX_GRID_CONTENT_LIFT = 12.5`、临时兼容分支的下线触发条件（如“等待服务端 2.1 协议全量部署后移除”）。

#### 规约 3：JSDoc 规范
- 对外导出的公共接口、类、纯函数统一书写规范 JSDoc，明确入参前置条件、返回值语义与副作用；类内部私有实现采用单行或短段落精准描述核心不变式。

## 三、常量与单一真源（SSOT）优化方案

### 1. 现状痛点
- **局部散落魔法数与硬编码偏移**：如在多个 View 中各自分散写死 `y = 4`、`x = -26.376`、`duration = 0.68`，调优时顾此失彼。
- **视觉颜色未 Token 化且频繁在堆上分配**：View 中散落直接调用 `new Color(230, 30, 24, 255)`，既破坏了整体设计主题的一致性，又在渲染刷新时产生高频临时对象。
- **双真源（Double Source of Truth）冲突**：配表已有数值，代码中又留了一份“表缺失时的兜底值”，两份产生漂移，难以判断以谁为准。
- **TypeScript 传统 Enum 带来转译包袱**：传统 enum 转译后生成双向映射闭包对象，影响包体且阻碍 Tree-Shaking。

### 2. 治理规约与分层管理

#### 规约 1：分层常量体系
1. **物理与几何常量**：统一定义在对应的 Timeline 或 Presentation 模块（如 `HexGeometry.ts`、`ShakePresentation.ts`）。
2. **设计系统与主题 Token**：收拢至各子系统的主题模块（如 `TerritoryTheme.ts`、`ZCTheme.ts`），颜色常量通过 `Object.freeze(new Color(...))` 预实例化，只读复用。
3. **UI 文本与提示**：统一收拢至 `*Texts.ts`（如 `TerritoryTexts.ts`），禁止在业务分支中硬编码中文展示文案。
4. **配表与代码真源划界**：数值类事实以配表为单一真源；代码中的兜底仅作为静态安全守卫，并显式注释所映射的表列名。

#### 规约 2：使用 `as const` + 联合类型替代传统 Enum
```ts
// 🟢 推荐实践：零运行时开销，强类型自动推导，完美 Tree-Shaking
export const TERRITORY_STATION_STATE = {
    owned: 'owned',
    exploring: 'exploring',
    available: 'available',
    locked: 'locked',
} as const;

export type TerritoryStationState = typeof TERRITORY_STATION_STATE[keyof typeof TERRITORY_STATION_STATE];
```

## 四、架构设计与巨石类拆解方案

### 1. 现状痛点
- **巨石类（God Class）职责过载**：
  - `TerritoryMapView.ts`（4000+ 行）：融合了网格管理、节点池化、站点排版、云层散场、多类粒子特效播放、宝箱开箱特写与战斗过场迷雾。
  - `TerritoryModel.ts`（2800+ 行）：融合了领域状态机、位运算集合、网络写请求超时控制与 500+ 行的 ViewState 投影拼装。
  - 单一类修改牵一发而动全身，难以开展高内聚的单元测试。

### 2. 拆解设计方案（组合优先）

```
                  ┌───────────────────────────────────────────────┐
                  │                 TerritoryEntry                │
                  │              (Composition Root)               │
                  └───────┬───────────────────────────────┬───────┘
                          │                               │
                          ▼                               ▼
               ┌──────────────────────┐        ┌──────────────────────┐
               │ TerritoryController  │        │   MainTerritoryMap   │
               │ (Session/Intent Hub) │        │ (Page Container/UI)  │
               └──────────┬───────────┘        └──────────┬───────────┘
                          │                               │
        ┌─────────────────┼─────────────────┐             │
        ▼                 ▼                 ▼             ▼
┌──────────────┐  ┌───────────────┐  ┌───────────────┐ ┌──────────────────────┐
│TerritoryModel│  │Territory      │  │TerritoryWrite │ │   TerritoryMapView   │
│(Pure Domain) │  │Projection     │  │Coordinator    │ │(Grid/Viewport Core)  │
│              │  │(Pure Functions│  │(Network/Ticket│ └──────────┬───────────┘

                                         │(Fog Manager) │  │              │  │Player (FX)   │
                                         └──────────────┘  └──────────────┘  └──────────────┘
```

#### 拆解 1：Model 层职责三向正交拆解
1. **`TerritoryModel`（纯业务状态机）**：
   - 职责：维护地块解锁与通关状态（BitSet）、当前章节配置、野怪宝箱快照、开合规则校验。
   - 特征：纯 TypeScript 类，零 Cocos 引擎引用，零直接 I/O。
2. **`TerritoryProjection`（纯函数展示投影）**：
   - 职责：将领域模型数据无副作用地组装为只读 ViewState（HUD 文本、关卡详情弹窗内容、敌军阵容描述、背包汇总文本）。
   - 特征：纯函数输入输出，无内部可变状态，可独立脱离引擎进行极速单元测试。
3. **`TerritoryWriteCoordinator`（网络写请求状态机）**：
   - 职责：管理在途票据（`writeTickets`）、超时定时器、Loading 引用计数配对与竞态作废检查。
   - 特征：封装异步通信与重试协议，对 Model 屏蔽通信并发细节。

#### 拆解 2：View 层表现特效组合拆解
1. **`TerritoryMapView`（核心网格视图）**：
   - 职责：仅聚焦于六边形蜂窝排布、ScrollView 视口滚动、节点按 `cellId` 的 diff 复用与站点基础点击。
2. **`TerritoryRewardEffectPlayer`（奖励粒子播放器）**：
   - 职责：管理读数升起、倒圆锥抛物线喷发、飞向底栏英雄/卡牌按钮的 3 套对象池（`gainPool`、`burstPool`、`heroFlightPool`）与运动轨迹。
3. **`TerritoryCameraDirector`（镜头与转场导演）**：
   - 职责：管理宝箱开箱推镜拉近、章节切换镜头平移跟随、首次开战前的迷雾推镜过场。

## 五、落地实施路径与验证保障

1. **分阶段平滑演进**：
   - **Phase 1（低风险/高收益）**：常量的 `as const` 联合类型收敛与 Token 化，提取纯函数 `TerritoryProjection.ts`（已验证落地）。
   - **Phase 2（中风险）**：清除生产代码中的需求日记型注释，将历史变迁归纳到规范文档与提交日志；消除高频热路径的内联 Lambda。
   - **Phase 3（结构化拆解）**：将 `TerritoryMapView` 中的独立对象池和动画播放器剥离为 `TerritoryRewardEffectPlayer`。
2. **严格门禁与回归保障**：
   - 每一阶段均通过自动化测试守护边界：
     - `tests/territory-presenter.test.ts`（业务逻辑与并发状态机）
     - `tests/territory-mvc-boundary.test.ts`（架构分层与依赖纯度）
     - `npm run verify:hygiene` 与 `node tools/verify/verify.mjs defs`（门禁完整性）
