## 一、口径

1. **以 L1~L3 三列为准，不以「落地口径（modifier 建议）」列为准。** 该列在多处仍是上一轮旧值，已确认的冲突：
   - `101301 连发苔针`：L1 写「额外发射 **1** 发」，落地列写 `bulletNumFlat=2`（紫卡应为 1 发，金卡才是 2 发）。
   - `101702 噬血蔓延`：L 写溅射 `40/44/48%`，落地列写 `12/16/20%`。
   后续所有落地以 L 列文字为准，落地列的数值视为历史残留。
2. **一条技能 = 一条 `skillChainId`，三档 `replace`**，`selectZCSkillPlans` 只取当前等级最高的一档 ⇒
   三档之间不叠加，写错 `accumulate` 会让三档一起生效。
3. **同条混搭（一条技能多个属性）** 计划行只能放一个 `statId`。方案：主属性照旧放 `statId/operation/value`，
   额外属性写进 `skillParamJson` 的 `mix.<statId>[.addRate]`（新增引擎支持，见第五节），不改表结构。

#### 三、结算：友军通道与 `hit` 互斥

`ZCProjectileSystem.update` 里，友军扫掠**先于**敌军扫掠执行，且整条通道是独立的：

| 约束 | 为什么 |
| --- | --- |
| 不参与碰撞、不消耗 `remainingPierces` | 借它扣一次 = 「路过的友军替你挡了一发穿透」，穿透卡会被自己人吃掉名额 |
| 不改 `baseDamage`、不过 `pierceFalloff` | 衰减是「同一发打多个敌人」的补偿，友军没挨打 |
| 不产生 `hit` 事件、不写 `hitUnitIds` | 写进去下次真的打这个单位会被当成「已命中」跳过 |
| 排除施法者本人 | 法师站自己子弹的起点上 ⇒ 每发都白送自愈，等于常驻回血被动 |
| 同一颗弹道对同一单位只回一次（`allyHealIds`） | 相邻两个扫掠步会在交界处重复接触同一个单位 |
| 额度归零立刻停（`allyHealLeft`） | 「一颗子弹最多给 N 个」是**每颗弹道**的额度，多弹幕各算各的 |

🔴 **额度必须拷到弹道上，不能每帧回查参数**：`skillParamJson` 是 `unitId:pvpSkillId` 一份，
一轮齐射 3 颗共享同一个 `allyPierceMaxCount` 就是「整轮齐射共享 3 次」而不是「每颗 3 次」。
同理血量比例也在出手时拷进去 —— 弹道在途时施法者可能已经死了，结算不该回头查技能运行时。

🔴 **比例按被治疗单位自己的 `maxHp` 算**（`unit.maxHp * pct`），不是施法者的。法师血少、
前排坦克血多，写成施法者的话这条被动对坦克几乎无效，恰好把「站后排把射程变成团队续航带」
的设计意图做反。

治疗走 `ZCStatusResolutionSystem.healUnit`：封顶 `maxHp`、死亡不生效、溢出丢弃、
不吃治疗加成、不碰护盾 —— 全部沿用既有口径，不新增一条治疗管线。

##### 1. 101404：为什么是「复用车道 + 新触发」而不是新车道

`summon_unit` 刚在 103103 落地，101404 与它**只差触发方式**：舞王是「冷却 12 秒」，这条是
「累计普攻 8 次」。于是 `applySummonUnit` 开头按 `summonEvery > 0` 分流，新增
`applySummonByCount`；计数器走独立的 `unit.summonFiredCount`：

- 不借 `summonReadyAt`（同卡 101403 菌丝突刺有冷却，共用会变成「放完分身、突刺也进冷却」）；
- 不借 `counterFiredCount`（101401 连击也在数普攻）；
- 记的是 `completedAttackCount` 的**上次快照值**，第一次推进只记基线、不补放；被拒（参数不全）不消费次数。

`summonFollow` **不配**：设计 N 列只要求「只做普通攻击与被动」，而固定阵位只有 4 个 ——
6 只分身会两两叠在同一个角上，那是**静默的画面错**（结算全对、看起来像 3 只）。

##### 2. 102204：`team_aura` 与 `team_buff` 只差「有没有窗口」

光环是常驻的，嗜血术是「开 N 秒、每 CD 开一次」。新增一条车道而不是给光环加开关，
是因为「有没有窗口」会连带改变三件事：`killCount` 归因、延长记账、以及「离开范围即失去」。

三处不写就会静默错：

| # | 坑 | 后果（不报错） | 处置 |
| --- | --- | --- | --- |
| 1 | 续挂时长写成「整段窗口」 | N 列要求「友军离开范围即失去」，整段续挂会变成「走了还亮着」 | 续挂 `TEAM_BUFF_REFRESH_SECONDS = 0.6`（与 `TEAM_AURA_SECONDS` 同档），且只续到受惠者自己的截止时刻 |
| 2 | 延长按**施法者**的击杀算 | 设计 N 列是「延长在每个目标自身的状态上独立计时」 | 每个受惠者各存 `teamBuffKillBase` / `teamBuffExtendUsed`，按自己的 `killCount` 增量延长，封顶按「已延长总秒数」判 |
| 3 | 把「延长」当成「重置窗口」 | 窗口 8 秒、CD 8 秒 ⇒ 16 秒时「窗口关」与「CD 到」是同一刻，会被读成「开始下一轮」 | 用例直接钉这个边界：拼接式续挂得 16，重开得 24.05 |

`killCount` 只在 `ZCDamageResolutionSystem.damageUnit` 里由**打出最后一击的人**累加；反射打死的不记
（那条路径没有归属，硬算会把功劳记到挨打的人身上）。

##### 3. 102304：减攻挂 `attackPct`，不是 `damageRatePct`

设计写的是「降低攻击」。`attackPct` 抬/降的是**面板**，`damageRatePct` 只在结算处乘一次、面板上看不见 ——
两者都能让伤害变小，但对玩家的可读性完全不同。状态 id `__roar:<pct>:<秒>__`，同参数复用同一条定义。

护盾三条口径都在一处兑现：量 = **施法者**最大生命 × 15%（设计 M 列「自身 15% 最大生命」，
不是受惠者自己的）、取 `Math.max(现有, 新)` 不叠加、写 `shieldExpireAt` 到期由 `expireShield` 清零
（清零不清 HP ⇒ 不会变相回血）。

半径内一个敌人都没有 ⇒ 拒放（不写 `roarReadyAt`），否则对空气吼完白吃 8 秒 CD。
CD 走独立的 `roarReadyAt`：同卡 102303 冲锋占着 `dashReadyAt`、102301 光环每帧续挂不要 CD。

##### 4. 102004：`storm_zone` —— 「会飘」和「会拽」各是半个新车道

设计 N 列有两句话，各对应一处新代码：

- 「移动速度 10px，方向随机变化」⇒ `ZCGroundZoneSystem.advanceWander`：每 `wanderTurnSeconds` 抽一个新朝向
  写回 `moveVelocityX/Y`，**位移仍走原来那句「有速度就推」**。自己再推一次就是双倍速。
  🔴 抽方向必须走 `context.random`（对局种子）；`Math.random` 会让同一份快照在回放 / 重算时飘出不同路径，
  而且**一条错都不报**。
- 「牵引敌人」⇒ `pullEnemies`。N 列说「与已有的 legacy_traction 完全契合」，但那条车道的力心是**单位坐标**
  （挂在施法者身上），套过来会变成「把人往三叶小丑身上拽」；设计要的是往**风心**拽，而风心每秒换向。
  所以算法与常量照抄（只拽敌方、最小距离 `20 × combatDistanceScale`、每步 `speed × dt` 且不超过
  「到最小距离的剩余」），只把力心换成区域圆心。**牵引放在圆心定死之后**（`followCaster` 之后），
  早一步会按上一帧的圆心算方向，风一转向就出现「人被往回甩一下」。

另两条与既往相反的判断：

- **不设 `hitOncePerUnit`**：那是「同一个敌人全程只挨一次」（101303 的接触判定），这条设计明写
  「每 0.5 秒造成 10%」，站在风里就得一直挨 ⇒ 靠 `waveInterval = 0.5` 复打。
- **场上没有敌人不拒放**（与怒吼相反）：区域活 6~8 秒、还会飘，敌人走过来照样挨打、照样被拽。

表现复用 `风法师_龙卷风`（新建 `ZCStormFx.ts`，与 101303 同一份美术）。资源清单必须按 **68020**
单独收一遍：`zcWindBarrageEffectPaths` 只按 68013（风炮菇）收，三叶小丑收不到 ——
漏收的症状是「照常掉血、场上一团风都没有」，与第 16 批同一条坑。

#### 三、🔴 一个必须记住的运行时事实：`behaviorKey` 由同袋第一条决定

`68035:30709` 这一袋里住着四条链（103501 / 103502 / 103503 / 103504）。构筑期
`ZCMatchRuntimeCompiler` 为每个 `${unitId}:${pvpSkillId}` **只建一条 runtime**：

```ts
const merged = mergeSkillPlanIntoRuntime(runtimes.get(key), plan, loadout.targetUnitId);
if (merged) { runtimes.set(key, merged); continue; }   // ← 已有就只并参数，不换 behaviorKey
```

于是运行时里的 `behaviorKey` 恒等于**第一个创建它的计划行**那个值（这里是 103501 的
`skill_params`），后面整袋换车道的链改不动它。这不是 bug，是「一卡一袋」的必然结果，但它
意味着两件事必须分开看：

| 用途 | 该读哪里 | 读错的后果 |
| --- | --- | --- |
| **车道分发**（触发系统走哪条分支） | `parameters` 里有没有那个前缀的键（`rayEvery`） | 以为要走 `behaviorKey === 'ray_beam'` 的分支 ⇒ 技能一声不响地不触发 |
| **表现收拢**（本局加载哪些 prefab） | **表行**的 `behaviorKey`（`ZCVisualResourcePlan` 读 `adapters.skillPlans`，是原始计划行） | 读 runtime 那个 ⇒ 收不到路径 ⇒ 照常掉血、屏幕上一道光都没有 |

用例 `tests/zcds-ray-beam-batch18.test.ts` 的端到端那条专门把这件事钉住：
断言的是「参数进了 runtime」+「**表行** behaviorKey 能取到 prefab」，而**不是**
`runtime.behaviorKey === 'ray_beam'`（那样断言会红，且红得让人以为实现错了）。

#### 二、口径（用户拍板）：没到解锁等级 ⇒ 连"放"都不放

先试过「把未解锁链的**形状参数**补齐」（`skillParamFloor`，只兜 `zone*`）——
低等级能飞出形状正确的 3 道旋风，但那是**凭空多出一个未解锁技能**，被用户否掉。
最终改成**门控**：没解锁 ⇒ 这一击按普通普攻打，什么都不放。

| 技能通道 | 原来怎么放 | 现在 |
| --- | --- | --- |
| `pvpSkill.empoweredSkillId`（武将技那一击） | 基表 `empoweredEvery` 计数到点就放，**与等级无关** | **本次新增门控**：主链未全解锁 ⇒ `empowered` 归零 |
| `pvpSkill.secondarySkillId`（副轨，如横扫 30832） | `secondaryCooldown > 0` 才放 | 天然已门控（未解锁时参数袋没有这个键） |
| 投枪 `lanceEvery` | 同上，参数驱动 | 天然已门控 |
| 触发系统各车道（`chain_damage` / `team_buff` / `roar` / `storm_zone` / `summon_unit` …） | 靠 `skillRuntime` 里的车道参数 | 天然已门控（未解锁 ⇒ 没有运行时） |

#### 三、判据：为什么是「主链全解锁」而不是「技能 id ↔ 链 id」映射

`pvpSkill` 与 `pvpSkillPlan` 之间**没有**「技能 id ↔ 链 id」这一列（`pvpSkillPlan.pvpSkillId`
指的是**普攻行**，不是武将技行），所以没法直接问「30831 属于哪条链、几级解锁」。

全表实测给出了结构层面的替代判据：**每张卡 `pvpSkillPlan` 的最后一条主链都是 `100x04`，
解锁等级 12 / 24 / 36，而它的 `skillParamJson` 恰好就是那个武将技的行为参数**
（暴风 `zone*` / 豌豆机关枪 `burst*` / 迪斯科旋风 `zoneSelfCentered` / 飓风 `storm*` /
大吼大叫 `roar*` / 嗜血术 `teamBuff*` …）。于是：

> **主链（`100000~109999`）里只要还有一条没解锁 ⇒ 这个单位的武将技不许放。**

- 只看主链：辅助链（`19xxxx` / `28xxxx` / `37xxxx`，解锁一路排到 22~23 级）不参与，
  否则会把 12 级就该解锁的武将技拴到 22 级。
- 按「链的最低已解锁档」判，不按行判：`replace` 模式一条链只生效最高档，
  `100101@3/10/22` 在 12 级时算已解锁。

#### 二、缝隙的量化根因（不是摆位算错）

`spriteFrame` 的 rect 底边与「有像素的内容」并不重合：旧图内容画到 raw y=264、rect 底边在 297

修法（`ZCChainLightningFx` + 两处调用）：

1. `zcChainArcPieceLayout` 新增 `offsetX/offsetY`：节点沿长轴**后退** 1 屏上（= 0.39 世界 px），
   有像素的那一截才落在段起点；
2. `stretch` 的除数从 rect 全长换成**可见长度** `93.333 − 1 − 2 = 90.333`（屏上）⇒ 内容长度正好 = `step`；
3. 额外留 **2 px 重叠**吃掉笔锋那行淡像素；
4. `ZCAttackResolutionSystem.pushChainArc` 与 `ZCGameModel.syncFollowingCombatEvents` **两处**都加偏移
   （漏一处 = 首次施放贴合、敌人一动又裂开）；
5. 段数仍按 rect 全长 93.333 算（少了是真的没东西可画），满段 `stretch ≈ 1.03`，只动长轴不变粗。

## 六、第 24 批（2026-11-19）：强化普攻的表现口径 = 「同 prefab ×1.2」

### 背景

`pvpSkill` 的一对列 `empoweredSkillId`（几乎每张卡都有）让同一张卡在「每 N 次普攻 / 每 X 秒」那一发
切到**另一条技能行**（36xxx / 308xx），而那条行**自带一份美术**：

| 卡 | 普攻 prefab | 强化那一击原来播的 prefab |
| --- | --- | --- |
| 68023 民兵 | `民兵普攻_刀光` | `民兵_武将技能` |
| 68022 雷蕉 | `雷弹攻击`（+ 三角形拖尾） | `雷法师_武将闪电` ← 用户看到的「蓝白惊雷」 |
| 68011 冰法师 | `冰法师_普攻` | 冰雕 |

玩家侧的表现是「同一张卡每 5 秒突然变成另一个技能」，读不出这是加强；资源侧则要维护两份美术。

### 定案

用户 2026-11-19：「使用 A 方案，所有 35 张卡牌包括怪物卡的强化普攻和普通攻击的特效一致，
只是特效的大小放大 20%」。

| 项 | 口径 |
| --- | --- |
| 弹体 / 区域主特效 | 一律 `attackProfile.effectPrefabPath`（普攻行） |
| 命中附加特效 | 一律 `attackProfile.impactEffectPrefabPath`（普攻行）—— 36231 的这格是空的，原来强化击连命中特效都没有 |
| 尺寸 | 事件级 `effectScale = 1.2`（`ZC_EMPOWERED_FX_SCALE`） |
| 判定 | **一个字节都不动**（`collisionRadius` / `areaRadius` 不跟着放大） |
| 玩法口径 | `skillId` / `mode` / `damageRate` 等仍取技能行，`event.empowered = true` 不变 |

### 为什么走 `effectScale` 而不是 `sizeScale`

`sizeScale`（磁电菇「巨囊弹体」101602 那条）在出手时**同步乘进了 `collisionRadius`**，用它做「看着大 20%」
等于顺手把命中半径也放大 20%。`effectScale` 只进视图的 `node.setScale`，纯表现。

### 边界（唯一一处）

- `68009 仙桃行者`：普攻行**本来就没有专属美术**（近战，走通用 `hit` 表现）。它的强化那一击保持
  「没有专属美术」，与普攻一致 —— 这不是缺陷。
- 主动技能另起一条独立车道（`ZCSkillTriggerSystem` → `resolveRadialSkill` / 区域波次）的那几张卡，
  它们的区域表现仍按自己的 prefab 播；本批只管「强化那一击」。

### 验证

- `tests/zcds-model.test.ts` 新增「强化那一击的表现口径（定案 A）」：扫全表 33 个有强化的单位，
  逐拍断言「任何一拍都不许出现武将技专属美术」+「至少 20 张跑出『同 prefab ×1.2』」。
- 同文件两条双链用例（`every_seconds` / `every_n_attacks`）从「改用技能行 prefab」改写为「同 prefab ×1.2」。
- `tests/zcds-*` 全量：无新增红（唯一新增是 node 测试运行器的 IPC 抖动，单跑 9/9 绿）。

## 十二、第 30 批（2026-11-20 下午）：闸门放行后飓风又不动了

### 二、两处修法

1. `ZCAttackResolutionSystem.stormDeliveryTarget`（新增）：锁定目标不是**活单位**时，按与闸门扫描
   **逐条对齐**的条件（跳过同阵营 / 尸体 / 打不了空的飞行单位）重扫一次，射程用
   `ZCTargetingSystem.attackReach`，挑最近的活敌当投送目标。射程外的不追（宁可就地生成）。
   ⇒ 「闸门放行 ⇒ 必有落点」。
2. `applyStorm` 加第二道闸：`release` 把「锁定目标在射程内」也算有目标，而那个目标**可能是一堵墙**
   ⇒ 再判 `nearestEnemyDistance ≤ attackReachOf`（两个 hook 缺任一就退回只吃 `release`，夹具不受影响）。
   只在打墙时不再往脚下扔风。

顺带修掉一处早就坏掉的 import：`ZCUnitDefinition` 在 `ZCAttackResolutionSystem` 里只剩使用、没有导入，
`tsc` 一直报 TS2304（外部进程剪掉的，与本批无关）。

### 三、口径更正

三叶小丑 68020 的普攻射程是 **300 表值 = 90 世界 px**（`skillAttr 502203`「三叶小丑普攻攻击距离」），
前两批文档里写的 260 表值 = 78 世界 px 是错的，§13.3 / §33.9 已一并订正。

  射程外的不追；1 秒后位移落在 28 px 的直线上；

## 十三、第 32 批（2026-11-20 傍晚）：打空口径确认 + S 型游走 + 蘑菇爆炸的抛掷弧线

## 十四、第 33 批（2026-11-20 晚）：分裂菇分身的生成表现

用户三条原话：「分身生成坐标落，落在以本体为圆心，20px 为半径的圆内」/
「每个分身生成有 0.1s 的间隔差」/「分身时，在分身坐标先播放【分裂菇_生成分身】，
再出现分裂菇分身，分裂菇的分身透明度约为 65%」。

### 一、为什么这不是「纯表现」

原来 6 只分身在同一拍 `spawnUnit`、坐标全在本体脚下。要让「先特效、后出现」成立，
**推迟的必须是 `spawnUnit` 本身**：隐藏一个已存在的单位解决不了问题 —— 它仍是合法目标
（会被看不见的东西挨打），也会自己往敌人方向走开（出现时已不在那个坐标上）。

所以新建 `state.pendingSummons` 队列：每条记两个时刻 `fxAtSeconds`（推特效事件）与
`spawnAtSeconds`（真正出生，= fx + 0.32s），`flushPendingSummons()` 在 `advance()` 里
`flushDeferredBarracksSpawns` 之后、`updateUnits` 之前兑现。队列里存的是**施法那一刻**
算好的继承属性与散落坐标 ⇒ 本体中途阵亡也照样出生（独立分身的裁定本来就是「血量为 0 才消失」）。

### 二、四条「不写就静默错」

1. **队列进快照**：0.6~0.9s 的真状态，读档 / 重连丢队列 = 白丢 6 只分身
   （累计普攻次数已经消费）。`ZCSnapshotCodec` 校 `spawnAtSeconds >= fxAtSeconds` 等 6 项。
2. **排队中的份算进 12 只上限**：只数 `state.units` 会让第二次召唤看见「场上 0 只」。
3. **`markSummon` 在兑现时也要补**：`spawnUnit` 注册的那一刻它还不是召唤物。
4. **角度按序号均分 + 随机抖动**：6 只共用一颗随机数会叠成一个点（看着像只召出 1 只）。

### 三、特效资源（美术只给了散帧）

`分裂菇_生成分身/` 下 26 张 1185×1185 散帧，没有 prefab / anim / atlas。补 `tools/build_fission_spawn_fx.py`：

- `_sizeMode = 0`（CUSTOM）+ `_isTrimmedMode = false` + contentSize = **原始画布 1185**
  —— 裁剪框从 171×172 一路长到 912×868，按 frame_01 定画布会把整段爆发压成一小坨；
- `wrapMode = 1`（Normal，播一遍），`_duration = 26/24 ≈ 1.0833`，与模型常量
  `ZC_SUMMON_SPAWN_FX_SECONDS` 必须逐位一致（短了后段爆发看不到，长了末帧定格）；
- 屏上尺寸由 `TARGET_BURST_SCREEN_PX = 120`（**最大那一帧**的宽度）反算 `SCALE = 0.131579`。

路径登记 `ZC_EFFECT_PATHS.fissionSpawn` + 行为键 `summon_unit`，**不进 `warmup`**。

### 四、透明度 65% 走的是既有通道

`unit.summonAlpha` → `ZCUnitView.applySummonAlpha`（宿主 `UIOpacity` 级联 spine+血条+轮廓）。
配表 `summonAlpha` 优先（舞王 103103 = 0.6）；101404 三档都没填 ⇒ 用
`SUMMON_INDEPENDENT_ALPHA = 0.65` 兜底，**只兜独立分身**，普通召唤仍是实心。
