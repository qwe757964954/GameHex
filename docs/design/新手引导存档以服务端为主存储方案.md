# 新手引导存档：以服务端为主存储

- 范围：`assets/script/app/guide`、`assets/script/app/bootstrap/guide`、`assets/script/app/net` 的读包行为
- 前置结论：协议源在协议仓（`client_proto/` 只是镜像），本方案不单侧改 `.proto`
- 状态：P0 客户端改造已落地（2026-11-16），协议扩展仍待后端

## 1. 结论与边界

以服务端为主存储**可以落地**，但不能直接把"读回包覆盖本地"。

服务端在现有协议里只能表达一个进度游标（`funcId + step1 + step2`，`protoCompiled.proto:4937-4962`），表达不了：

- 是否跳过结束（`skipped`）
- 已展示/待补发的奖励台账（`grantedSteps`）
- 引导表版本（表在 `remoteRef` bundle，可热更，`RefUtil.ts:16-27`）
- 首次进入时间（`startedAt`）

因此目标形态定为：

> **服务端持有权威进度游标；本地存档降级为「缓存 + 待发队列 + skipped/granted 载体」，而不是被删除。**

只要这三类信息仍然只存在于本地，"服务器主存储"就必须是双源合并，而不是单源覆盖。

分两阶段：

- **P0（本方案，纯客户端）**：服务端游标 + 本地缓存/待发队列 + 合并取更后者。协议不动。
- **P1（需后端配合）**：补 `skipped` / `granted` / 表版本 / 时间戳，才谈得上"完全以服务端还原"。

## 3. 目标数据流

**读（启动）**

```
start()
  ├─ store.load()            // 同步，先出首帧，不等网络
  ├─ restoreGuideProgress()  // 本地进度立即 publish
  └─ gateway.load()          // 异步
        ├─ null / 0-0        → 不校正（本地是唯一进度）
        └─ 有游标            → 展开成前缀 → mergeSave → 若前进则重建 GuideProgress + publish + persist
```

**写（推进）**

```
notify / skip
  ├─ progress.complete()
  ├─ store.save()            // 本地立即落盘（缓存）
  ├─ outbox.push(stepId)     // 持久化待发，跨页面/进程存活
  └─ gateway.flush()         // 顺序发送，业务成功才出队
```

**冲突裁决**（三种情况，均落到同一个函数）

| 情况 | 判据 | 结果 |
| --- | --- | --- |
| 服务端落后（丢包 / 旧游标） | 远端游标更靠后，或本地 `completed` 更长 | 保留本地不倒退；启动时把本地最后完成步补推（等价整条前缀），outbox 继续补发。队列丢失时也能让服务端重新追上 |
| 本地为空（换机/清缓存） | 本地 `load()` 为 null，远端有游标 | 采用远端前缀 |
| 服务端领先 | 远端游标不在本地 `completed` 内且更靠后 | 采用远端，重建 UI |

## 4. P0 落地内容（已完成）

| # | 文件 | 实现 |
| --- | --- | --- |
| 1 | `model/GuideSaveStore.ts` | 新增 `IGuideRemoteCursor`；`guideOwnerKeySuffix(owner)` 让存档与待发队列共用同一 key 口径；`remoteCursorToData(cursor, steps)`：`0/0` 或表外 stepId → `null`，否则按「最后已完成步」展开成完成前缀 + 下一步；`applyRemoteCursor(cursor, steps, now)` 走 `mergeSave`，用 `hasSameProgress`（忽略 `updatedAt`）判断是否真前进，只在前进时写盘 |
| 2 | `model/GuideSyncOutbox.ts`（新增） | 持久化待发队列：`push`（同 `stepId` 去重）、`head`、`ack`、`prune(completedIds)`、`clear`；坏 JSON / 版本不符 / 结构不对一律按空队列；`owner=null` 只进内存；key `guide.outbox.v1.server:<id>:role:<id>`；纯 TS，不 import cc |
| 3 | `application/GuideGateway.ts` | 上报返回三态 `ok / retry / invalid`：断线、`dispose`、`succ!==1`、异常 → `retry`；`stepId` 非 `数字-数字` 或任一段为 0 → `invalid`；读侧 `0/0` 返回 `null` 并打日志 |
| 4 | `application/GuideStorageAdapter.ts` | 删除 `createGuideSaveStore`，改 `createGuidePersistence()` 一次返回 `{ store, outbox }`，共用一份 storage 与同一 owner |
| 5 | `application/GuideController.ts` | `start()` 改为「本地首帧 → `load()` → `adoptRemoteCursor()` → `flushOutbox()`」；校正用 `restoreGuideProgress(store, steps)` 从合并后的存档重建实例；远端无游标时 `pushLocalProgress()` 补推最后完成步；`syncProgress` 入队后由 `drainOutbox` 串行发送（`retry` 停、`invalid` 告警后 ack、`await` 后先判 `isDisposed`），`flushing` 防并发 |
| 6 | `bootstrap/guide/GuideComposition.ts` | 接线改为 `const { store, outbox } = createGuidePersistence()`，同时传入 Controller |

与初版设计的差异：

- 原 #6（给 `GuideProgress` 加公开构造入口）**没有做**：`restoreGuideProgress` 已能完成「存档 → 实例」，再加一个入口会多一条链校验路径。
- 原 #5 的「`persist()` 里入队」**改到 `syncProgress(stepId)`**：`persist()` 只负责本地落盘，入队只发生在带 stepId 的真实推进点，避免校正 / 初始化也产生待发项。
- 老玩家迁移实现为「启动时补推最后完成步」：游标按最后已完成步解释，推最后一步即等价于整条前缀，不需要逐步重放。
- 实际 `firstRun` 口径：`saved === null`；远端校正成功后显式置 `false`，其余情况不动。

## 5. 协议契约（前置，必须后端确认）

P0 能否成立，取决于下面每一项；任意一项给不出答案，服务端就只能当"参考"，不能当主存储。

| 契约项 | 现状 | 需要确认 |
| --- | --- | --- |
| `step1/step2` 语义 | 客户端上报"刚完成的步"（`GuideGateway.ts:79`） | 服务端存的是"最后已完成"还是"当前待做" |
| `0/0` 语义 | 读写两侧不对称（写得拒 0，读不拒） | 建号是否预置 0/0；0/0 是否等于"从未开始"。**实测 2026-11-16：全新账号首次 `GuideInfoRspMsg` 回 `{funcId:1, step1:0, step2:0}`**，客户端按"未开始"处理；仍需确认记录被服务端清空时是否也是 0/0 |
| 单调性 | 未知 | 服务端是否只接受更靠后的步；乱序/重发是否回退 |
| 行数 | `CmdFunctionGuideInfoRspMsg.infos` 是 required 单条 | 确认每个 `funcId` 只有一行 |
| 跳过 | 只上报最后一步 | 是否需要区分"跳过"与"走完" |
| 校验 | 未知 | 是否校验 JSON 之外的服务端进度合法性（防作弊） |

建议按"服务端取大"落地：接收上报时只在链序更靠后时更新，回包返回最终值。这样 outbox 重发天然幂等，也不怕乱序。

## 6. P1 协议扩展（需后端，proto2 必须 optional）

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `guideVersion` | optional uint32 | 引导表版本；表热更后游标才有意义 |
| `skipped` | optional uint32 | 区分跳过/走完，保住 `wasSkipped` 表现 |
| `grantedSteps` | optional bytes 或 repeated uint32 | 奖励台账；为将来"凭 stepId 幂等补发"提供依据 |
| `updatedAtMs` | optional uint64 | 双端取新（`GuideSaveData.updatedAt` 已为此预留，`GuideSaveStore.ts:42`） |

proto2 下新增字段必须 `optional`；新增 `required` 会直接打挂老服务端/老客户端。

## 7. 本地存档在新架构下的保留边界

| 场景 | 为什么仍必须本地 |
| --- | --- |
| 首启/断网 | `GameNet.instance.isConnected === false` 时查询与上报都空转（`GuideGateway.ts:44-47`、`:73`） |
| 首帧同步 | `start()` 同步返回、`publish()` 立即渲染，不能等网络 |
| 写失败窗口 | `allowRetry=false` 的丢包路径真实存在（见 §2） |
| 切页/进对局 | 主界面与战斗各建一次 `GuideComposition`（`MainPageComposition.ts:64`、`BattleComposition.ts:64`），进度要接续 |
| `skipped` / `grantedSteps` | 协议无字段，只能本地补 |
| 表热更跨版本 | 游标可能对不上新表，本地还有"步已删除 → 从首个未完成继续"兜底（`GuideProgress.ts:156-160`） |
| 编辑器预览 | `owner=null` 只写内存，不污染真账号（`GuideSaveStore.ts:77-79`） |

## 8. 迁移

1. **老玩家（本地有档、服务端 0/0）**：已实现为启动时 `pushLocalProgress()`——把本地最后完成步入队补推。游标按最后已完成步解释时，这一步等价于整条前缀；服务端取更大即幂等。否则 0/0 会把已走到 `6-1` 的玩家打回第一步。
2. **服务端是旧游标（非 0/0 但落后）**：同样在启动时补推最后完成步。实测出现过本地到 `5-1`、服务端仍 `1-3` 的情况，靠这条把服务端拉回来，避免只在 0/0 时才迁移。
2. **新玩家**：服务端 0/0 + 本地 null → `firstRun=true`，正常从 `1-1` 开始。
3. **同一账号双端**：按链序取更后者；`skipped` 取或、`grantedSteps` 取并集（沿用 `mergeSave`）。
4. **存档 schema**：`GUIDE_SAVE_VERSION` 不变；outbox 单独用 `guide.outbox.v1` 前缀，不混进存档结构。

单测覆盖点：

- `guide-save-store`：游标 `0/0` 与表外 stepId → `null`；首位 / 中间（`6-3` → `7-1`，前缀 14）/ 末位（`8-1` → 结束）；领先采用且保留 `startedAt`；落后不倒退；本地为空时采用远端前缀。
- `guide-controller`：远端领先只校正一次并二次 publish；远端落后不倒退；`0/0` 保持 `firstRun`；启动补发遗留待发项；失败保留并按 FIFO 重试；校正后裁掉已完成待发项；老玩家迁移补推最后完成步；远端旧游标（`1-3`）落后于本地（`4-1`）时补推 `4-1`。
- `guide-gateway`：`succ===1` 才是 `ok`；断线 / 异常 → `retry`；非法 stepId → `invalid`；读侧 `0/0` 返回 `null`。
- `guide-sync-outbox`：FIFO、同 step 去重、跨会话冷读、账号隔离、坏 JSON 三种形态、`prune`、预览态不落盘。

尚未执行的手工 / 联调场景：

- 真机断网完成两步再联网，核对服务端最终游标与本地一致。
- 换设备登录同一角色，确认从服务端游标续上、本地缓存不再被当成权威。
- 完成一步后立刻切页 / 进战斗，确认待发项不丢、下次启动补发。

## 10. 未决项与风险

1. **协议契约仍需后端确认**：`step1/step2` 是「最后已完成」还是「当前待做」、`0/0` 语义、服务端是否单调取大、是否每个 `funcId` 单行、跳过如何表达。当前假设全部收敛在 `remoteCursorToData` 一个函数里，确认后只改这一处。
2. **P1 协议扩展未做**：`guideVersion` / `skipped` / `grantedSteps` / `updatedAtMs` 只在本方案中定义，`client_proto` 未改（协议源在协议仓，不能单侧修改）。
3. **`0/0` / 旧游标与「服务端重置」不可区分**：启动补推会把本地进度写回服务端；若后端需要清零引导，必须提供额外信号，否则清不掉已完成的老账号（非 `0/0` 的旧游标同样会被补推覆盖）。
4. **未执行真机 / 联网联调**：见 §9 的场景清单；断网、换机、切页丢包三条路径目前只有单测覆盖。
5. **未跑全仓测试**：只跑了 `tests/guide-*.test.ts`、装配守卫与主界面组合用例；全仓 `npm test` 可能受无关模块影响，未作为本次判据。
6. **其他消费方未确认**：服务端是否已有别的模块读取 `CmdFunctionGuideInfo`（如功能解锁 gate），仓库内查不到，需后端确认改口径的影响面。
