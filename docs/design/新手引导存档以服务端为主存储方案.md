# 新手引导存档：以服务端为主存储

- 范围：`assets/script/app/guide`、`assets/script/app/bootstrap/guide`、`assets/script/app/net` 的读包行为
- 前置结论：协议源在协议仓（`client_proto/` 只是镜像），本方案不单侧改 `.proto`
- 状态：设计待确认，未改代码

## 1. 结论与边界

以服务端为主存储**可以落地**，但不能直接把"读回包覆盖本地"。

服务端在现有协议里只能表达一个进度游标（`funcId + step1 + step2`，`protoCompiled.proto:4937-4962`），表达不了：

- 是否跳过结束（`skipped`）
- 已展示/待补发的奖励台账（`grantedSteps`）
- 引导表版本（表在 `remoteRef` bundle，可热更，`RefUtil.ts:16-27`）
- 首次进入时间（`startedAt`）

因此目标形态定为：

> **服务端持有权威进度游标；本地存档降级为「缓存 + 待发队列 + skipped/granted 载体」，而不是被删除。**

只要这三类信息仍然只存在于本地，"服务器主存储"就必须是双源合并，而不是单源覆盖。

分两阶段：

- **P0（本方案，纯客户端）**：服务端游标 + 本地缓存/待发队列 + 合并取更后者。协议不动。
- **P1（需后端配合）**：补 `skipped` / `granted` / 表版本 / 时间戳，才谈得上"完全以服务端还原"。

## 3. 目标数据流

**读（启动）**

```
start()
  ├─ store.load()            // 同步，先出首帧，不等网络
  ├─ restoreGuideProgress()  // 本地进度立即 publish
  └─ gateway.load()          // 异步
        ├─ null / 0-0        → 不校正（本地是唯一进度）
        └─ 有游标            → 展开成前缀 → mergeSave → 若前进则重建 GuideProgress + publish + persist
```

**写（推进）**

```
notify / skip
  ├─ progress.complete()
  ├─ store.save()            // 本地立即落盘（缓存）
  ├─ outbox.push(stepId)     // 持久化待发，跨页面/进程存活
  └─ gateway.flush()         // 顺序发送，业务成功才出队
```

**冲突裁决**（三种情况，均落到同一个函数）

| 情况 | 判据 | 结果 |
| --- | --- | --- |
| 服务端落后（丢包） | 远端游标已在本地 `completed` 内 | 保留本地，outbox 继续补发 |
| 本地为空（换机/清缓存） | 本地 `load()` 为 null，远端有游标 | 采用远端前缀 |
| 服务端领先 | 远端游标不在本地 `completed` 内且更靠后 | 采用远端，重建 UI |

`firstRun` 口径同步调整：

```
firstRun = 本地 load() == null && 远端无有效游标
```

远端查询失败时退回现有口径（`saved === null`），不要因为网络问题把老玩家判成新玩家。

## 5. 协议契约（前置，必须后端确认）

P0 能否成立，取决于下面每一项；任意一项给不出答案，服务端就只能当"参考"，不能当主存储。

| 契约项 | 现状 | 需要确认 |
| --- | --- | --- |
| `step1/step2` 语义 | 客户端上报"刚完成的步"（`GuideGateway.ts:79`） | 服务端存的是"最后已完成"还是"当前待做" |
| `0/0` 语义 | 读写两侧不对称（写得拒 0，读不拒） | 建号是否预置 0/0；0/0 是否等于"从未开始" |
| 单调性 | 未知 | 服务端是否只接受更靠后的步；乱序/重发是否回退 |
| 行数 | `CmdFunctionGuideInfoRspMsg.infos` 是 required 单条 | 确认每个 `funcId` 只有一行 |
| 跳过 | 只上报最后一步 | 是否需要区分"跳过"与"走完" |
| 校验 | 未知 | 是否校验 JSON 之外的服务端进度合法性（防作弊） |

建议按"服务端取大"落地：接收上报时只在链序更靠后时更新，回包返回最终值。这样 outbox 重发天然幂等，也不怕乱序。

## 6. P1 协议扩展（需后端，proto2 必须 optional）

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `guideVersion` | optional uint32 | 引导表版本；表热更后游标才有意义 |
| `skipped` | optional uint32 | 区分跳过/走完，保住 `wasSkipped` 表现 |
| `grantedSteps` | optional bytes 或 repeated uint32 | 奖励台账；为将来"凭 stepId 幂等补发"提供依据 |
| `updatedAtMs` | optional uint64 | 双端取新（`GuideSaveData.updatedAt` 已为此预留，`GuideSaveStore.ts:42`） |

proto2 下新增字段必须 `optional`；新增 `required` 会直接打挂老服务端/老客户端。

## 7. 本地存档在新架构下的保留边界

| 场景 | 为什么仍必须本地 |
| --- | --- |
| 首启/断网 | `GameNet.instance.isConnected === false` 时查询与上报都空转（`GuideGateway.ts:44-47`、`:73`） |
| 首帧同步 | `start()` 同步返回、`publish()` 立即渲染，不能等网络 |
| 写失败窗口 | `allowRetry=false` 的丢包路径真实存在（见 §2） |
| 切页/进对局 | 主界面与战斗各建一次 `GuideComposition`（`MainPageComposition.ts:64`、`BattleComposition.ts:64`），进度要接续 |
| `skipped` / `grantedSteps` | 协议无字段，只能本地补 |
| 表热更跨版本 | 游标可能对不上新表，本地还有"步已删除 → 从首个未完成继续"兜底（`GuideProgress.ts:156-160`） |
| 编辑器预览 | `owner=null` 只写内存，不污染真账号（`GuideSaveStore.ts:77-79`） |

## 8. 迁移

1. **老玩家（本地有档、服务端 0/0）**：首次连接必须**先上推本地**，再拉取；否则 0/0 会把已走到 `6-1` 的玩家打回第一步。
2. **新玩家**：服务端 0/0 + 本地 null → `firstRun=true`，正常从 `1-1` 开始。
3. **同一账号双端**：按链序取更后者；`skipped` 取或、`grantedSteps` 取并集（沿用 `mergeSave`）。
4. **存档 schema**：`GUIDE_SAVE_VERSION` 不变；outbox 单独用 `guide.outbox.v1` 前缀，不混进存档结构。
