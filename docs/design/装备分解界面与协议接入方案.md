# 装备分解界面与协议接入方案

> 状态：已落地（数据层 + 独立分解弹窗，2026-11-25）。入口、筛选、5 列装备网格、勾选、收益汇总与整组请求均已接进 `Role.prefab` 运行时；界面按蓝湖效果稿落地。旧的角色装备页内联分解模式保留代码但已无入口，仅作历史实现追溯。

![装备分解效果图](../../outputs/equip-decompose/equip-decompose.png)

## 1. 结论

- 老端的「装备分解」是**背包多选页**：筛选阶级 / 品质、最多勾 99 件、实时算精炼石返还、一次请求分解；入口在角色 → 装备页的「一键分解」按钮（老端复用了名为 `按钮_一键合成` 的按钮）。
- 新端目前只有**单件分解**（装备详情弹窗 → `RoleController` 走 `equipGrowth.request('CmdEquipDecomposeReqMsg')`），没有批量页、没有筛选和收益汇总。
- **当前协议本身支持一组分解**：`CmdEquipDecomposeReqMsg.tlUniqueIds` 是 repeated，老端也是一次把整组 id 发过去；新端默认同样一次整包发。
- 本轮把**数据层**补齐：分解收益口径、可分解候选、99 件上限、筛选 / 全选 / 勾选规则、整组请求与回包解析都已经有唯一实现，并补了单测。
- 服务端若只实现单件 / 只回部分 id，客户端才按「缺件逐件补发」兜底；正常流程不逐件请求，也不展示逐件进度。
- 界面最终按**独立弹窗**落地（2026-11-25）：装备页签「装备分解」不再把背包列表切成内联多选，而是打开 `EquipDecomposePopup`。弹窗为 720×1280、面板 660×1080，顶部木牌标题 + 两条筛选（阶级 / 品质「及以下」）、中间 5 列 96 格装备网格（视口 560×500、横距 20、纵距 18）、已选 / 全选、底部精炼石收益板与取消 / 分解按钮；底部说明与「关闭后不可找回」按效果稿保留。旧的内联分解模式仅保留历史代码，不再有入口。

### 1.1 当前弹窗的界面口径

| 区域 | 规格 | 行为 |
| --- | --- | --- |
| 筛选 | 285×56，默认「全部 / 全部」 | 下拉首行为「全部」（回到不筛），阶只列背包实际出现的阶（1..20），品质列 1..7；切到具体档清空已选并自动全选命中项 |
| 网格 | 600×566 板，560×500 视口，5 列 96 格 | `decomposeCandidates()` 过滤后渲染；超过 99 件只选前 99；上下滑动提示常驻 |
| 勾选 | 右上角勾，已选 / 99 | 点击格切换；满 99 提示；「全选筛选结果」重选当前筛选命中项 |
| 收益 | 600×146 板 | `decomposeSummary(ids)` 实时算 `gain`；精炼石图标 + `× N` +「（预计）」；右侧「分解 N 件 / 关闭后不可找回」 |
| 操作 | 取消 231×108、分解 321×108 | 取消 / 关闭 / 点空白关闭；分解经 `RoleEvent.Intent { kind: 'decompose' }` 整组提交，回包后关闭并刷新背包 |

效果稿源文件在 `outputs/equip-decompose/equip-decompose.png`（HTML/CSS 同目录），切图在 `assets/resources/image/main/panel/equipdecompose/`（ASCII 命名）。

筛选口径（2026-11-26 修正）：`CmdEquipItem.curQuality` 是 `equipRank.qualityLevel`（1..17 品质档），不是界面品质；`RoleRepository.readEquipBag()` 按 `(rank, qualityLevel)` 将该行的 `quality`（1..7）换算后写入 `IRoleBagEntry.quality`，供筛选、品质框、排序使用。阶数上限从 `equipRank.rank`（1..20）取，不再硬编码 6；筛选状态在 `onOpen` 重置为「全部」，按钮标题显示当前值。

## 2. 老端口径（迁移依据）

| 项 | 老端实现 | 新端对应 |
| --- | --- | --- |
| 入口 | `TabRoleEquip` 的「按钮_一键合成」→ `CtrlAlert.OpenLayerEquipBreak()` | 角色 → 装备页新增「一键分解」入口 |
| 列表数据 | `ModelEquipItem.GetItemBagDatas()`：只取背包装备，已穿戴的在 `VOEquipPartBag`，天然不进列表 | `RoleRepository.decomposeCandidates()` 同样只取 `_equipBag` 且 `!equipped` |
| 筛选 | `GObjSelect`：`1..maxRank` 的「N 阶及以下」、品质「N 及以下」；切换筛选会清空已选并自动全选命中项 | `EquipDecomposeTable.decomposeFitsFilter()` + `autoSelectDecompose()`；本端另加「全部」行（`rank/quality = -1`），阶选项由 `decomposeRankOptions()` 只列背包实际出现的阶 |
| 数量上限 | `EQUIP_BREAK_MAX_99` = 99；超过提示 | `EQUIP_DECOMPOSE_MAX` = 99，勾选 / 全选 / 发请求三处都收口 |
| 单件收益 | `equipRank[rank, baseQuality].decompose` + `floor(costNum × equipDecomposeGainPer / 100)` | `EquipDecomposeTable.equipDecomposeGain()`，装配到 `IRoleBagEntry.decompose` |
| 请求 | `CmdEquipDecomposeReqMsg { tlUniqueIds }` | `RoleRepository.decomposeEquips(ids, caller, { onProgress, mode })` |
| 回包 | `tlUniqueIds`（真正移除的）+ `tlCmdGoods`（返还） | 原样返回 `IRoleDecomposeResult`，缓存由 `applyGrowthResponse` 同步删除 |
| 空列表 | 老端「分解」按钮直接 return，「暂时没有可分解的装备」文案 | `decomposeEquips([])` 返回 `failed`，界面提示「请选择装备」 |

注意：老端 `GetBaseEquipRankRef()` 取的是 **`baseQuality`（基础品质）**，不是当前升品后的 `curQuality`；升品消耗通过 `costNum` 以 70% 比例返还，所以同阶装备的返还仍会因为养成投入不同而不同。

## 3. 协议与配置

```
CmdEquipDecomposeReqMsg {
    repeated sint64 tlUniqueIds;   // 本次要分解的装备唯一 id
}
CmdEquipDecomposeRspMsg {
    repeated sint64 tlUniqueIds;   // 服务端实际移除的 id（可能只接受一部分）
    repeated CmdGoods tlCmdGoods;  // 返还物品，当前是精炼石
}
```

| 配置 | 用途 | 缺行时 |
| --- | --- | --- |
| `equipRank[rank, qualityLevel].decompose` | 品阶基础返还 | 按 0 计，不崩 |
| `gameConfig.equipDecomposeGainPer` | 养成投入返还比例（当前 70） | 用 `EQUIP_DECOMPOSE_DEFAULT_GAIN_PER = 70` 兜底 |
| `gameConfig.equipAddQualityCostId` | 返还物品 resId（当前 10100 精炼石） | 仓库给 `0`，界面隐藏产出图标，不伪造物品 |

服务端回包才是权威：`removedIds` 与 `rewards` 都按回包展示；客户端不自行从 `tlUniqueIds` 推测奖励，也不在回包前先删缓存。

### 3.1 协议支持一组，逐件只是缺件兜底

`tlUniqueIds` 是 `repeated sint64`，一组 id 可以放在同一条请求里，老端和新端默认都这么做。下面的逐件补发**只在服务端实现不完整时兜底**，不是正常流程：

1. 默认整包发一次（与老端一致，界面不显示「正在分解」，只把底部按钮置灰）；
2. 整包 `failed`（超时 / 离线）→ 直接失败，不再逐件重试，避免 99 次超时叠加；
3. 整包 `ok` 但回包缺件（服务端只接受部分 id）→ 只对缺件逐件补发，`onProgress(completed, total)` 上报；
4. `mode: 'sequential'` 可直接逐件发，仅用于后端明确只支持单件的联调场景。

奖励优先用回包 `tlCmdGoods`；回包没有 goods 时，界面只显示本地预计，不假设已经到账。部分失败时保留未分解的勾选，已成功的件不再重复提交。

### 4.2 状态

| 状态 | 表现 |
| --- | --- |
| 空候选 | 网格区显示「暂无可分解装备」，底栏收益 0，分解按钮置灰 |
| 未选择 | 已选 0 / 99，收益 0，分解按钮置灰 |
| 选择中 | 选中格橙色描边 + 绿色遮罩 + 对勾；收益按选中集合实时汇总 |
| 达到 99 | 再点未选格弹「一次最多分解 99 件装备」，不改变已选 |
| 提交中（正常） | 一次整组 `CmdEquipDecomposeReqMsg`；**不显示「正在分解」遮罩或进度条**，只把底部分解按钮置灰 |
| 提交中（缺件兜底） | 仅服务端只回部分 id 时仓库内部逐件补发，界面不展示逐件进度 |
| 成功 | 退出分解模式、恢复完整装备列表、弹现有奖励弹窗；列表与角色红点刷新 |
| 失败 / 超时 | 保持分解模式与选择，Toast 提示，不假设装备已删除 |

正常流程不出现任何「正在分解 / 分解中」等待态；`equip-decompose-batch.png` 与 `equip-decompose-progress.png` 仅保留作历史效果稿，不再作为本次实现口径。

### 4.3 交互规则

1. 点格子切换选中；品质框本身不响应点击，命中区域覆盖整格。
2. 切换阶级 / 品质筛选：清空已选，再自动全选命中的前 99 件（老端行为，减少重复点选）。
3. 「全选」：只选当前筛选命中且未穿戴的装备，满 99 停止。
4. 分解前不弹二次确认，保持老端一步完成；底部条明确显示「分解 N 件」与预计返还。若策划后续要求高价值装备二次确认，另开确认弹窗，不塞进本模式。
5. 排序沿用背包：品质降序 → resId → uniqueId；不做「按返还排序」，避免与背包认知不一致。

## 8. 风险与边界

| 风险 | 处理 |
| --- | --- |
| 协议支持一组，但服务端只实现单件 / 整包被忽略 | 默认整包请求；整包 `ok` 但回包空 / 缺件时逐件补发；`mode: 'sequential'` 仅供联调；整包超时则直接失败，不叠加 99 次超时 |
| 服务端不返回 `tlCmdGoods` | 界面只显示本地预计（`（预计）`），不假设到账；成功后按 `removedIds.length` 提示件数 |
| 服务端只接受部分 id | 以回包 `tlUniqueIds` 为准；补发只针对缺件，已成功的件不重复提交 |
| `equipRank` 缺 `(rank, baseQuality)` 行 | 先回退 `(rank, curQuality)`；仍缺按 0 计，不阻塞分解 |
| `Long` 精度 | 全程用十进制字符串 id（`toIdString` / `normalizeDecomposeIds`），不转 number 比较 |
| 99 件上限被筛选 / 手选叠加突破 | 勾选、全选、发请求三处都截到 99 |
| 已穿戴装备混入 | 候选只取背包 `!equipped`；服务端仍会兜底 |
| 配置比例为 0 / 缺行 | 0 视为坏配置，回退 70%；产出 resId 缺失时隐藏图标 |
| 效果稿与运行时差异 | 效果稿是 720×1280 设计稿，不是引擎截图；本次以 `Role.prefab` 内联模式为准，真机验证后如需替换再更新图 |
