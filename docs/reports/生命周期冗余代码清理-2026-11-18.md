## 0. 结论摘要

- 生产代码删除 **15 处**已证明冗余的生命周期实现：

### 2.1 为什么不是“把守卫搬到另一层”

- 删除的布尔门闩没有在下游补替代判断：属性赋值本身不叠加监听，不需要新的门闩。
- 删除的 `onDestroy` 停表没有改成 `onDisable` 停表：Cocos 销毁顺序已保证停表先于 `onDestroy`，再加一层属于重复。
- `BigMapController` 的外层守卫没有下移到 `releaseInputs` / `super.dispose`：它们本来就是幂等的，不需要新包装。

## 3. 多层 dispose 专项

### 3.1 大地图四层链

`BigMapController.dispose()` → `BigMapModel.dispose()` → `BigMapCampRepository.dispose()` / `BigMapSlgRepository.dispose()` → `GameNetBigMapCampGateway.dispose()` / `GameNetBigMapSlgGateway.dispose()` → `GameNet.removeCaller(this)`。

| 层 | 守卫与职责 | `super.dispose()` 前后 | 下游幂等性 | 重复可达性 | 结论 |
| --- | --- | --- | --- | --- | --- |
| `BigMapController` | 原 `isDisposed` 早退；无独有清理 | 前：`releaseInputs()`、`model.dispose()`；后：`super.dispose()` 释放 scope | `offTarget` 幂等；Model 有守卫；scope 有 `_disposed` | 组合层与测试均可双调用 | **A，已删除** |
| `BigMapModel` | 守卫；负责释放两个 Repository | 前：清世界 / 选中态等；后：`super.dispose()` | Repository 有守卫 | 双 dispose 可达 | **B**：它是保证“依赖仓库只释放一次”的真实边界 |
| `BigMapCampRepository` / `BigMapSlgRepository` | 守卫；各自负责释放一个 Gateway | 前：清缓存；后：`super.dispose()` | Gateway 有守卫 | 双 dispose 可达 | **B**：保护“网关只释放一次”的可观测契约 |
| `GameNetBigMapCampGateway` / `GameNetBigMapSlgGateway` | 守卫；`removeCaller(this)` 是网络归属解除 | 前：置 disposed；后：无 | `removeCaller` 本身幂等 | `tests/bigmap-camp-move.test.ts:247-249` 显式双 dispose 后 `removed` 深等于 `[gateway]` | **B**：最内层必须只解除一次，测试钉住 |
| `ControllerBase` / `ResourceScope` | 无 dispose 早退；各自幂等 | — | `offTarget` 幂等、`scope.dispose()` 有 `_disposed` | — | 不作为子类守卫的替代 |

**结论**：不能因“基类已经判断”删除内层守卫。`BigMapController` 之所以是 A，是因为它自身在 `super.dispose()` 之前没有任何“只能做一次”的副作用；一旦某层负责的是网关解除、loading 配对或弹窗关闭，就必须保留该层守卫。

### 3.2 领地链

`MainTerritoryMap.onDestroy()` 先 `EventMgr.emit(TerritoryUiEvent.Disposed)`（第 653 行），再 `emit(VIEW_LIFECYCLE destroyed)`（第 654 行）；后者经 `MainPageComposition.dispose()` → `own(() => controller.dispose())` 再触发一次。

| 层 | 职责 | 删除后的影响 | 结论 |
| --- | --- | --- | --- |
| `TerritoryController.dispose()`（`TerritoryController.ts:160`） | 守卫后：`releaseInputs()` → `model.dispose()` → `stopOutput()` → `stopOutput=null` → `super.dispose()` | `TerritoryModel.dispose()` 本身无守卫；第二趟会再次 `loadId += 1`、`cancelInteraction()`、按 `loadingPushes` 逐次 `hide` 全屏 loading。loading 是引用计数，重复 hide 会破坏配对，留下遮罩 / 提前关闭遮罩 | **B，保留** |
| `TerritoryModel.dispose()`（`TerritoryModel.ts:752`） | 无守卫；作废在途加载、取消交互、清章节与缓存、撤掉本页 loading | 依赖 Controller 守卫保证只进一次 | **B（无守卫本身不是冗余）** |
| `TerritoryController.stopOutput` | 解除自己注册的 Model 输出订阅 | `TerritoryModel.dispose()` 会 `outputs.clear()`，但订阅方应自己退订自己订阅的输出；现行测试与规范要求“Model 收尾 → 退订输出 → 释放资源”顺序 | **B，保留** |

### 3.3 ZCDS 战斗链

`ZCBattleController` / `ZCBattleRuntimeController` / `ZCBattleSettlementController` 的守卫均在 `super.dispose()` 之前拦截 `leave()`、`phase.leave()`、`cancelRequests()`、关弹窗等动作。第二次进入会重复发离开协议 / 重复取消请求 / 重复关弹窗，均有可观测副作用，且 `ZCBattleController` 还有 `onRuntimeDestroyed` 事件入口与初始化失败 `catch` 两个真实入口，故为 **B**。

### 3.4 视图与弹窗层

- `TerritoryStationView.dispose()`：第二次会访问已销毁的 `iconSprite.node` 等并可能抛错，中断销毁链；`tests/territory-station-batching.test.ts:263-264` 双 dispose 依赖该守卫，**B**。
- `PopupBase.close()` 的 `_closeHandled`：缓存弹窗第二次 `close()` 时 `PopupManager.owns(this)` 已为假，会走 fallback `node.destroy()`，毁掉缓存节点，**B**。
- `PopupBase._internalClose()` 的 `_closeHandled`：它承担 `onClose`、取消 `_openContext`、解绑空白关闭的“只做一次”职责，**B**。
- `PopupBase.onDestroy()` 的 `_resourceScope.dispose()` + `removeCallerListener`：节点可未经 `close()` 直接销毁，必须有兜底，**B**。
