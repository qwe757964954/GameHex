# 主角单位规则与研发说明（Captain）

> 状态：待评审（2026-11-26，第 6 版）。本文只给规则与落地方案，**未改任何源码、未改任何源表**；需要动的表全部列在 §7，等评审通过后统一改。
> 适用：PVP / 异步匹配等常规对局。塔防（`config.pveDefence` 存在）**不产主角**。
> 角色定位：主城自带的守卫单位，自动巡逻、自动开战，玩家不可操作；带养成（天赋 + 皮肤）。

---

## 0. 一句话

**开局立即产 1 个主角**，之后主城按 **30s** 重产（间隔写在 1001 行 `soilderAddTime`），场上恒限 1 个；主角在主城周围 **3 格（126 逻辑 px）** 内随机巡逻，**120 px** 内发现敌人就主动开战，**开战后不换目标、追击无上限**；打完回巡逻圈；主城被拆后改以**最近的己方建筑**为圆心（主角继续存活，只是不再复活），己方建筑全没了就**全图自由巡逻**；主角阵亡后**主城重新开始倒计时**，到点再产（即"复活"）。
主角是**主城 2002 产出的新单位（unitId 1001）**，养成上**替代旧的民兵**：吃「角色天赋」（原民兵天赋）成长，以及**按皮肤张数**给的基础属性加成。**皮肤决定打法**——当前两张：**刺客守护（远程 700/0.75）**、**重剑守护（近战 400/1.1）**，每张皮肤各带 **1 个主角技能**。**主角没有职业**，只有「攻击方式（近战 / 远程）」这一个区分。

> **三条线，各管一件事，不许交叉**：**张数管属性**（已拥有皮肤去重计数 → `leadSkinCollect` 查档）｜**星级管技能**（该皮肤重复次数，封顶 5）｜**使用中管打法**（外观 / 普攻方式 / 技能档位，零属性收益）。

> 本版新增：开局立即产出、`soilderAddTime = 30s`、主城被毁主角继续存在、**养成与皮肤**（§6）、**皮肤决定攻击方式与技能**（§6.4）、**升星只升技能 / 张数只加属性**（§6.4.1 / §6.4.2）、**超 5 星转溢出**（等回收活动）。
> 口径更正：主角**有自己的单位 id（1001）**，不是 66014、也不是 2002。66014 只是**养成数据源**（天赋曲线 + 皮肤组），两者靠一条显式映射 `captainTalentArmyId = 66014` 关联，不靠 id 相同。

## 1. 先统一口径（这三条不统一，实现必分叉）

| 项 | 取值 | 依据 |
| --- | --- | --- |
| 1 格 = ? 逻辑 px | **42** | `HEX_GRID_LOGICAL_ROW_STEP`（`core/hex/HexGridLayout.ts:47`）。列的步长是 36，本规则统一按行距 42 折算 |
| 3 格半径 | **126 逻辑 px** | 3 × 42。与现有追击上限 `CHASE_MAX_DISTANCE = 3 * HEX_GRID_LOGICAL_ROW_STEP` 同口径 |
| 坐标口径 | 一律用**世界逻辑 px** | 单位位置是 `freeX / freeY`，与 `map.hexes[].x/y` 同一坐标系。**不要**用视图 px（视图行距 90，会放大 2.14 倍） |

### 1.1 「寻敌 120px」和「攻击射程」是两个不同的东西

| 概念 | 含义 | 取值 |
| --- | --- | --- |
| **侦测半径**（searchRadius） | 主角主动找目标的最远距离 | 120 逻辑 px（可配） |
| **攻击射程**（attackReach） | 真正能出手的距离 | 由 **1001 行**（主角卡行）的单位列算出：`(unitAttackRange + 目标体半径 × 0.5) × combatDistanceScale`。**使用中的皮肤可以覆盖 `unitAttackRange`**（§7.4），近战短、远程长 |

- `combatDistanceScale = 0.3`（`pvpGlobal`），所以**表里的 `unitAttackRange` 约等于世界 px 的 3.33 倍**。
- 想让主角「走 120px 才够得着」→ `unitAttackRange` 填 **400**（(400 + 22×0.5) × 0.3 ≈ 123 px）。
- 想让主角「近身砍」→ 填 **150~200**（≈ 48~63 px），主角会走到敌人脸上再打。
- 攻击射程公式与普通卡牌完全一致（`ZCTargetingSystem.attackReach`），这是需求里「寻敌逻辑和其他卡牌一致」的落点。

> 🔴 不要把 120 直接填进 `unitAttackRange`：那样实际射程只有 36 px，主角会贴到脸上才出手，和「120px 主动去攻击」的预期差 3 倍。

## 2. 行为规格（策划向状态描述）

### 2.1 概念状态

表现层继续用现有 `ZCUnitBattleState`（`born / idle / move / attack`），另用一个可选字段 `captainPhase` 区分「巡逻 / 战斗 / 归位」，**不新增枚举值**。

| 状态（captainPhase） | 玩家看到的样子 | 单位在干什么 |
| --- | --- | --- |
| `spawn`（battleState = born） | 从主城里冒出来 | 出生 0.2s，站着不动 |
| `patrol` + `idle` | 原地站着、偶尔转头 | 在巡逻圈里歇一会儿（0.6~1.4s） |
| `patrol` + `move` | 在基地附近溜达 | 朝一个圈内的随机点直线走 |
| `combat` + `move` | 朝某个敌人冲过去 | 已锁定目标，正在接近（**允许出圈、不设上限**） |
| `combat` + `attack` | 贴身/抬手打人 | 在攻击射程内，按攻击间隔出手 |
| `return` + `move` | 往基地走 | 战斗结束且在圈外，回锚点 |
| `dead` | 倒地消失 | 等主城重新产（复活） |

### 2.2 状态机

```
   主城计时器到点（开局立即一次）
        │
        ▼
   ┌──────────┐  0.2s   ┌─────────────┐  到点，歇 0.6~1.4s  ┌──────────────┐
   │  spawn   │ ──────▶ │ patrol/move │ ──────────────────▶ │ patrol/idle  │
   └──────────┘         └──────┬──────┘ ◀────────────────── └──────┬───────┘
                               │            选新巡逻点               │
             120px 内有敌人 / 受击(仇恨) │                          │ 距锚点>126（兜底）
                               ▼                                   ▼
                        ┌─────────────┐                      ┌──────────┐
                        │ combat/move │ ◀── 目标在射程外 ──  │  return  │
                        └──────┬──────┘                      └────┬─────┘
                               │ 进射程                           │ 到锚点
                               ▼                                  │
                        ┌──────────────┐  目标死/失效              │
                        │ combat/attack│ ─────────────────────────┘
                        └──────┬───────┘      （圈内直接回 patrol）
                               │ hp ≤ 0
                               ▼
                        ┌──────────┐   主城重新计时（soilderAddTime = 30s）
                        │   dead   │ ─────────────────────────────▶ spawn
                        └──────────┘   （主城已毁 ⇒ 不再产，永久消失）
```

### 2.3 迁移表（这张表就是程序要写的全部条件）

| # | 当前 | 条件 | 下一 | 要做的动作 |
| --- | --- | --- | --- | --- |
| 1 | `spawn` | `stateTime ≥ 0.2s` | `patrol/idle` | 记 `patrolWaitUntil = now + rand(0.6, 1.4)` |
| 2 | `patrol/idle` | `now ≥ patrolWaitUntil` | `patrol/move` | 采样一个圈内巡逻点 |
| 3 | `patrol/move` | 距巡逻点 ≤ 2px | `patrol/idle` | 清巡逻点，重设停留时间 |
| 4 | `patrol/*` | 侦测半径 120 内存在**合法敌方单位** | `combat/move` | 锁定该目标（最近优先，同距取 id 小） |
| 5 | `patrol/*` | `hatredUnitId` 有效且存活 | `combat/move` | **强制**锁攻击者，**忽略 120 半径** |
| 6 | `patrol/*` | 距锚点 > 126 | `return` | 朝锚点走（正常不该发生，兜底） |
| 7 | `combat/move` | 目标进入攻击射程 | `combat/attack` | 面向目标，按 CD 出手 |
| 8 | `combat/attack` | 距目标 > 攻击射程 × 1.3 | `combat/move` | 继续接近（滞回，与卡牌一致） |
| 9 | `combat/*` | 目标死亡 / 失效 / 进 `disengagedUnitIds` | `return` 或 `patrol/idle` | 清目标；圈外回 `return`，圈内回 `patrol/idle` |
| 10 | `combat/*` | —— | —— | **没有追击上限**：不按时间、不按距离放弃目标，只有迁移 9 会丢锁 |
| 11 | `return` | 距锚点 ≤ 2px | `patrol/idle` | 重设停留时间 |
| 12 | `return` | `hatredUnitId` 有效 | `combat/move` | 被打断归位，先打人 |
| 13 | 任意 | `hp ≤ 0` | `dead` | 清记账 + **把主城产主角计时器清零**，主城存活则重新倒计时 |

### 2.4 生成：主城产出机制

| 项 | 规则 |
| --- | --- |
| 产出源 | **只有主城**：`hex.building === 'hq' && hex.owner !== 'neutral' && isBuildingOperational(hex)`。兵营不出主角 |
| 产出间隔 | **主城卡行的 `soilderAddTime`（秒）**，初始 **30s**。填 0 或空 ⇒ 该主城不产主角 |
| 开局 | **立即产第 1 个**（不等第一个间隔），之后按 `soilderAddTime` 循环 |
| 场上上限 | **每方 1 个存活**（硬规则，不做配置项；便于调试可留 `captainMaxPerBase=1`） |
| 计时器 | 独立时钟，key 用 `captain:<hqHexId>`，存在 `state.spawnClocks`（与 `barracks:` / `mine:` / `tower:` 同一套机制） |
| 产出动作 | `spawnUnit(owner, hqCard, hex.tier, hqHexId, ignoreUnitCap = true)` → 落点为主城格中心 + 半格偏移（复用 `SPAWN_OFFSET_RADIUS`）。`hqCard.unitId` = **1001**（主角自己的单位 id，见 §7.1） |
| 主角阵亡 | **计时器清零**（`delete state.spawnClocks['captain:<hqHexId>']`）⇒ 从 0 重新倒计时 30s ⇒ 到点产新的（即"复活"） |
| 主城被毁 | 产出停止（`building` 变 `'none'` 后条件不成立）。**已存在的主角继续存活**，按 §2.8 锚点规则行动；只是**不再复活** |
| 塔防 | `config.pveDefence` 存在 ⇒ **所有席位都不产**（判断放在产出入口） |
| 人口 | 不占 `unitCapPerSide`，也不计入 `ZCUnitRegistry.count()` |
| 品级 | 主角 `tier` = 主城 `tier`（主城升品级，主角一起变强，沿用现有 `unitHpPerTier / unitAttackPerTier`） |
| 与兵营产兵的区别 | **不复用** `ZCEconomySystem.tickBarracks`：它写死 `building !== 'barracks'` 就跳过，且间隔会被 `spawnMinimumSeconds(3.5s)` 抬底、按品级递减。主角走独立 `tickCaptains`，间隔**直接取表值**，不夹取、不递减 |

> 🔴 **不要用 `card.cycleSeconds` 当产出间隔**：`parseCardCycleSeconds` 对主城（type=5）取的是 **`goldDigTime`（当前 6 秒，语义是产金）**，不是 `soilderAddTime`。图省事用它 ⇒ 主角每 6 秒复活一次，和策划填的数完全无关，且看起来"能用"，极难排查。

### 2.5 巡逻

**采样（圆内均匀分布，不能直接用 `r = R × random()`，否则会挤在圆心）**

```ts
const angle = random() * Math.PI * 2;
const r = R * Math.sqrt(random());
const px = anchor.x + Math.cos(angle) * r;
const py = anchor.y + Math.sin(angle) * r;
```

| 项 | 规则 |
| --- | --- |
| 锚点 | 有己方建筑时 = 该建筑格中心；无己方建筑时 = 无锚点 |
| 半径 R | 有锚点：`captainPatrolRadiusHex × 42`（默认 3 格 = 126 px）<br>无锚点：**不限制**，采样中心取主角当前坐标、R 取地图对角线一半（等价全图随机） |
| 移动方式 | 直线 `advanceTowardPoint`（`ZCMovementSystem.ts:107`），**不走 BFS 寻路**，也不写 `targetHexId / progress` |
| 移动速度 | **最终移速**（含天赋移速加成）× `captainPatrolSpeedScale`（默认 0.6） |
| 停留 | 到点后停 `captainPatrolIdleSeconds`（默认 1s，建议 0.6~1.4 随机） |
| 采样过滤 | 巡逻点落在地图外、或落在**敌方建筑 / 未破城墙格**上 → 重采样，最多 5 次；仍失败则原地停 1s |
| 阻挡 | 直线移动每步判一次落点格：若下一步会踩进敌方建筑 / 城墙格 → 就地停下、放弃本次巡逻点 |

> 巡逻只改连续坐标；`syncOccupiedHex` 照常更新所在格索引。

### 2.6 索敌与锁定（核心差异点）

| 规则 | 说明 |
| --- | --- |
| 主动索敌半径 | 120 px（`captainSearchRadius`），**只对敌方单位**生效。建筑 / 城墙不主动索敌（默认，见 §9-2） |
| 索敌口径 | 与卡牌一致：跳过自身 / 同阵营 / `hp ≤ 0` / `battleState === 'dead'` / 打不到空中时跳过 `flying` |
| 排序 | 距离最近优先，同距离取 id 小（复用 `ZCTargetingSystem.acquire`） |
| **战斗中不换目标** | 一旦锁定，**只有**下面 3 种情况会丢锁：① 目标死亡或移除；② 目标变成非法（同阵营 / 打不到的空中单位）；③ 目标进入 `disengagedUnitIds`。**不会**因为「出现更近的敌人」「受击产生新仇恨」「打建筑优先级」而换目标 |
| **追击无上限** | 目标跑多远都追，**不设超时、不设距离上限**。目标死亡/失效才回圈 |
| 巡逻态受击 | 受单位伤害时，`ZCDamageResolutionSystem.damageUnit` 已经写入 `hatredUnitId`（5s）。主角在 `patrol/* / return` 读到有效仇恨 → **直接强制锁定攻击者**，不再走 120px 半径与距离评分 |
| 巡逻态受击的例外 | 被**塔 / 建筑**打不会写仇恨（`source.kind !== 'unit'`），此时按普通索敌处理；这条与现有卡牌一致，不额外处理 |
| 禁止的行为 | 主角**不调用** `refreshPriorityTarget`（那是"被唤醒的怪 / 守家打建筑"的优先级通道，会把锁定抢走） |

**战斗分支伪代码（给程序直接对照）**

```ts
// 只有 current() 为 null 时才尝试重新索敌；绝不每帧 acquire 覆盖
const target = targeting.current(unit);
if (!target) {
    const forced = hatredValid(unit) ? hatredUnit : null;                   // 巡逻态受击 → 强制锁攻击者
    const acquired = forced ?? targeting.acquireWithin(unit, searchRadius); // 新增：带半径上限
    if (!acquired) { enterReturnOrPatrol(unit); return; }
    lock(unit, acquired);                                                   // 写 targetXxxId
}
if (targeting.isInAttackRange(unit) && now >= unit.nextAttackAt) startAttack(unit);
else if (超出攻击射程) advanceTowardPoint(unit, target.x, target.y, dt);      // 无上限，一直追
```

### 2.7 归位

- 触发：无目标 && 有锚点 && 距锚点 > 巡逻半径（含"追到很远，目标死了"的情况）。
- 行为：直线走向锚点，速度用**最终移速**（不用巡逻减速，回程要快）。
- 到达：距锚点 ≤ 2px 或已进入巡逻半径 → `patrol/idle`。
- 中途受击：立刻中断归位进入 `combat/move`（迁移 12）。

### 2.8 锚点重算

| 时机 | 规则 |
| --- | --- |
| 初始 | 锚点 = 自家主城格 |
| 主城被摧毁 | `damageBuilding` 把 `building` 置 `'none'`、`owner` 改成攻击方（`ZCDamageResolutionSystem.ts:97`）→ 立即重算 |
| 重算算法 | 在 `hex.owner === 自己 && hex.building !== 'none' && hex.hp > 0` 的格子里取**世界距离最近**的一个；同距取 id 小 |
| 没有己方建筑 | 锚点置空 → 巡逻不再受圆限制（全图随机） |
| 兜底自检 | 每 0.5s 复核一次「当前锚点格还是不是自己的建筑」，不一致就重算 |

> 注意：主城被拆后 `owner` 会变成攻击方，所以「己方建筑」不能用 `cardId` 或 `state === 'occupied'` 判，必须用 `owner + building !== 'none' + hp > 0`（与 `developedCount` 同口径）。

### 2.9 阵亡与"复活"

- `hp ≤ 0` → 走现有死亡流程（`markDead` / `transferDeath`）。
- 额外两步：① 清该席位的 `captainUnitIdByOwner` 记账；② **清零主城产主角计时器**（`captain:<hqHexId>`）。
- 之后由主城按 `soilderAddTime`（30s）重新倒计时，到点产新的主角 —— **这就是"复活"，没有单独的复活字段**。
- 主城已不存在 ⇒ 计时器没有宿主 ⇒ 不复活（永久消失）。
- 主角死亡**不影响**胜负判定（胜负仍只看建筑与比分，`ZCOutcomeSystem` 不改）。

## 3. 判定优先级（每拍从上到下，命中即 return）

```
1. hp ≤ 0 / dead            → 死亡清理（含计时器清零）
2. 硬控 controlOf           → 冻结（现有逻辑）
3. 冲刺 / dashChain         → 主角不参与，直接跳过
4. born 未满 0.2s           → 站住
5. 锚点复核（0.5s 节流）    → 更新 anchor
6. 仇恨有效？               → 强制锁攻击者（打断巡逻/归位）
7. 已有锁定目标？           → combat/move · combat/attack（不换目标、不设追击上限）
8. 120px 内有敌人？         → 锁定 → combat
9. 圈外？                   → return
10. 其余                    → patrol/move · patrol/idle
```

## 4. 与其他系统的边界

| 系统 | 结论 |
| --- | --- |
| 人口上限 | 不占。生成走 `ignoreUnitCap = true`，并在 `ZCUnitRegistry` 里按「非普通单位」记账（参考 `markSummon`） |
| 结算评分 | 建议**剔除**主角（否则「多一个免费单位」会让 `unitCount / totalUnitHp` 虚高）。需在 `ZCOutcomeSystem.scoreFor` 加过滤 |
| 兵营产兵 | 完全独立：`tickBarracks` 只认 `building === 'barracks'`，主角走 `tickCaptains`，互不影响 |
| AI | AI 不需要操作主角；AI 席位的视角下主角同样是自动单位 |
| 塔防 | 不产（`config.pveDefence` 判断放在产出入口，别放在行为分支） |
| 索敌系统 | 只加「带半径上限的索敌」这一个能力，不改现有 `acquire` 的评分规则 |
| 快照 / 读档 | 新增单位字段必须进 `ZCSnapshotCodec` 的还原白名单；`state.spawnClocks` 已随快照走，读档后倒计时能续上 |
| 多端一致性 | 随机采样消耗 `random()`，**必须**用局内种子随机（`this.random`），不能 `Math.random()` |
| 占领格 | 主角照常更新所在格（`syncOccupiedHex`），不额外加快占领 |

## 5. 表现需求（给美术/程序）

| 项 | 需求 | 现状 |

## 6. 主角养成与皮肤

### 6.1 五条硬规则

| # | 规则 |
| --- | --- |
| 1 | **天赋成长**：主角的养成线 = 旧游戏「角色天赋」（原角色天赋），即现有的 `armyLevel` 兵种 **66014** 这条曲线（201 级）。主角自己不是 66014，靠 `captainTalentArmyId = 66014` 这条映射取数（§7.2） |
| 2 | **收集数量 → 基础属性**：按「已拥有主角皮肤的**张数（去重）**」查一张分档表，给主角**基础属性**加成（攻击 / 生命，§6.4.2）。**只跟张数有关**：与是哪几张、每张几星、当前用哪张**全都无关**。**只有主角吃这份加成**，其他兵种不吃 |

> 一句话记法：**张数管属性，星级管技能，使用中管打法。**
>
> 🔴 **三条线各有各的输入，不许交叉引用**：
> - 属性 ← 皮肤**张数**（去重计数，重复不加张数）
> - 技能 ← 该皮肤的**星级**（重复次数，封顶 5）
> - 打法 ← **使用中皮肤**（本身零属性收益，也不影响技能档位）

### 6.2 数值叠加公式（唯一口径）

主角养成走的是**修改器（`skillAttrModifier`）+ 属性键映射（`pvpAttrMap`）**，不走 `pvpUnitGrowth`（该表的源表是 `doc/塔防数据配置/PVP-修改器适配.xlsx / PVP成长`，本稿不动它；哪天真要接，见 §9-28）。
最终值统一按 `ZCStatSchema.applyZCTypedUnitModifiers` 的公式算：

```
最终值 = (基础值 + flat 累加) × (1 + rate 累加) × 连乘因子
         ↑ 定额（operation=add）      ↑ 百分比（operation=addRate）
```

套到主角身上：

```
设 N = 已拥有主角皮肤的张数（按皮肤 id 去重，重复获得不增加 N）
  (战力%, 生命%) = leadSkinCollect[N]        // 查表，§6.4.2；缺行取不超过 N 的最大档

主角面板攻击 = (1001 行 unitAttack
              + Σ 天赋攻击定额)                 // 「角色攻击力」add，40 次 × +10
             × (1 + Σ 天赋伤害% )               // ⚠️ 见下方"伤害是独立乘区"
             × (1 + 张数攻击加成%)
             × (1 + 品级加成)
             × 全局 combatDamageMultiplier

主角面板生命 = (1001 行 unitMaxHp
              + Σ 天赋生命定额)                 // 「角色生命值」add，40 次 × +200
             × (1 + Σ 天赋生命% + 卡牌/转职 3%×次数 + 张数生命加成%)

主角面板移速 = (1001 行 unitMoveSpeed + Σ 天赋移速定额)

主角普攻伤害 = 面板攻击 × 招式倍率
             × (1 + Σ 角色伤害%)                // damageRate：只在伤害结算乘一次
```

> 🔴 **`damageRate`（角色伤害）不是 `attackPct`**。它只在伤害结算处乘一次，**不抬高面板攻击**，也不会被"按攻击力算"的公式二次吃到。所以上面把"天赋伤害%"单独列在结算行，不要塞进面板攻击。

> 🔴 **星级不进任何一条公式**。`leadSkinStar.star` 只读给技能档位（§6.4.1）。如果哪天在这里看到 `star`，就是写错了。

**不参与上面公式、而是由「使用中皮肤」决定的三项**：

| 项 | 来源 | 说明 |
| --- | --- | --- |
| 普攻方式 | 皮肤表的 `attackSkillId` → `pvpSkill.mode` | `melee` = 近战（无弹道）；`projectile` = 远程（有弹道与飞行时间） |
| 攻击射程 / 间隔 | 皮肤表覆盖值（缺省回 1001 行） | 近战射程短、远程射程长，**必须按皮肤配**，不能共用一套 |
| 主角技能 | 皮肤表的 `activeSkillId` + 该皮肤 `leadSkinStar.star` | 每张皮肤各 1 个，切皮肤即换技能；档位按 `star` 从 `pvpSkillPlan` 取（§6.4.1） |

- **先加后乘**：定额进 `flat`、百分比进 `rate`，两者是不同乘区，不会互相稀释。天赋与皮肤张数也各自独立乘区。
- 全部在**入局时冻结**（与 `unitRates` 现成通道一致），战斗中不读全局表。
- 攻速/暴击是否也吃天赋与收集，见 §6.3、§6.4.2 与 §9-7。

### 6.3 天赋（= 旧游戏角色成长）映射

数据源（**已存在，不用新建**）：

- `armyLevel` 表：66014 行共 **201 级**，每级 `attrList` / `modify` 指向 `skillAttrModifier`；
- `skillAttrModifier` 表：如 `26601404 → {'角色攻击力': 10}`；
- 服务端等级：`CmdArmyLevel`（`CacheMgr.getCmdArmyLevel(captainTalentArmyId)`，当前 = 66014）；
- 客户端已有 `MilitiaRepository` / `MilitiaTable.talentAttrsOf` 在做"≤ 当前等级累加"，但它**只输出展示字符串**，战斗要的是数字。

> 🔴 取数一律用 `captainTalentArmyId`（配置，默认 66014），**不要写死 66014、也不要拿主角 unitId（1001）去查这些表**：`armyLevel` 里没有 1001 行，查不到就是天赋全 0（且不报错）。

**每级是「增量」不是「累积快照」**：同一个修改器 id 在不同等级反复出现就反复累加。
原 66014 的 26601401 在 40 个等级各出现一次 ⇒ 累计 40 次。所以只需 6 个修改器，不必给 201 级各配一个 id。

| 天赋键（新表原文） | 类型 | 战斗影响 | 每次 | 次数 | 累计 |
| --- | --- | --- | --- | --- | --- |
| `角色攻击力` | **定额** `add` | `attack` flat | +10 | 40 | +400 |
| `角色生命值` | **定额** `add` | `maxHp` flat | +200 | 40 | +8000 |
| `角色暴击率` | **定额** `add` | `critRate` flat（百分点） | +0.25% | 40 | +10% |
| `角色暴击伤害` | **定额** `add` | `critDamage` flat（百分点） | +2% | 40 | +80% |
| `角色攻击间隔` | **定额** `add` | `attackInterval` flat（秒，负=更快） | −0.005s | 19 | −0.095s |
| `角色移速` | **定额** `add` | `moveSpeed` flat | +0.5 | 6 | +3 |

> 数值为**占位**，按紫卡（rarity=3，`pvpUnitGrowth` 里 50 级纯 flat、约 36 倍基础）缩放到"每级小额"。

**15 条卡牌解锁 / 转职节点**改走百分比，每条 `{'角色伤害': 3, '角色生命值百分比': 3}`：

| 类型 | 触发点 | 单条 | 满级累计 |
| --- | --- | --- | --- |
| `角色伤害`（`damageRate` addRate） | 6 卡牌 + 9 转职 | +3% | +45% |
| `角色生命值百分比`（`maxHp` addRate） | 同上 | +3% | +45% |

#### 6.3.1 修改器做定额 / 百分比的能力边界（代码实测）

| 需求 | 支持 | 依据 |
| --- | --- | --- |
| 攻击 / 生命 定额 | ✅ | `typedToLegacyPatch` 的 `attack` / `maxHp` 都有 flat 分支 |
| 暴击率 / 暴击伤害 定额 | ✅ 且**仅定额** | `STAT_TO_PATCH` 第二槽为 `null`，写 addRate 会乘不存在的 baseValue ⇒ 恒 0 |
| 移速 定额 | ✅ | `moveSpeed` 有 flat 分支（旧键 `移动速度` 的 scale 是 0.5，新键自定 scale=1） |
| 攻击间隔 定额 | ✅ | `attackInterval` flat 分支，负数 = 更快 |
| **伤害 定额** | ❌ | `damageRate` 只接受 `addRate`；注释原文「add 会变成 +0.1 点伤害，没有意义」 |
| **攻速 定额** | ❌ | `attackSpeed` 只接受 `addRate`；要做定额请改走 `attackInterval` |
| 同属性同时要定额+百分比 | ✅ 但需**两个 key** | `pvpAttrMap` 同一 legacyKey 只能一种 operation，重复且不一致会抛错 |
| 键没映射 | ⚠️ **静默丢弃** | `reportUnsupported` 只记进 `unsupportedAttributes`，不报错也不生效 |

### 6.4 皮肤（每张皮肤 = 一套打法）

**皮肤不是纯外观**：它同时决定模型、普攻方式、主角技能。三张已知皮肤：

| 皮肤 | 攻击方式 | 普攻 `pvpSkill.mode` | 主角技能 |
| --- | --- | --- | --- |
| 初始皮肤 | 近战 | `melee` | 1 个 |
| 魔剑士 | 近战 | `melee` | 1 个 |
| 寡姐 | 远程 | `projectile` | 1 个 |

> 🔴 **主角没有职业区分**。不要引入「战士 / 射手」职业字段、职业枚举或职业克制：这里只有**攻击方式**（近战 / 远程），实现上就是 `pvpSkill.mode` + 射程/间隔两个量。任何"主角职业"的写法都会在表现层、AI、索敌里多出一整套无意义分支。

| 项 | 规则 |
| --- | --- |
| 数据源 | `leadSkin` 表（按 `armyId = captainTalentArmyId` 过滤）。⚠️ 现有 3 行是旧占位（兽人/鱼人/骷髅民兵），**皮肤名单以最终美术为准**，初始 / 魔剑士 / 寡姐需要补行 |
| 外观 | `model` 列（已有） |
| 普攻方式 | 新增列 `attackSkillId` → `pvpSkill.skillId`。现有可直接复用：**30216 民兵普攻（melee 刀光）**、**30151 弓兵普攻（projectile 箭矢）**；魔剑士若要专属刀光再新开一行 |
| 射程 / 间隔 | 新增列 `attackRange` / `attackInterval`（按皮肤覆盖 1001 行）。近战 ≈ 150~200（实际 48~63 px），远程 ≈ 400（实际 ~123 px） |
| 主角技能 | 新增列 `activeSkillId`（1 个）。**每张皮肤各 1 个**，切皮肤即换技能 |
| **重复皮肤 → 升技能** | 同一张皮肤重复获得 ⇒ 该皮肤星级 +1（`leadSkinStar.star`，1~5）⇒ **该皮肤的主角技能升 1 档**（取 `pvpSkillPlan` 里对应 `skillLevel` 的行）。重复获得**不加任何属性**，只升技能；**5 星封顶**，超出部分记「溢出次数」等回收活动（§6.4.1） |
| **收集数量 → 基础属性** | **不是每张皮肤配一个值**。按「已拥有皮肤张数（去重）」查 `leadSkinCollect` 表得 `{攻击%, 生命%}`（§6.4.2）。与哪几张、星级、使用中全无关。重复获得同一张**不增张数、不加属性** |
| 使用中皮肤 | 服务端下发「当前使用皮肤 id」：决定外观 + 普攻方式 + 技能档位。客户端目前**没有这条协议**（`generated/requestMsg` 搜不到 skin），需要跨端确认 |
| 已拥有列表 + 星级 | 服务端下发「已拥有皮肤 id 列表」+ 每张皮肤的**星级**（≤5）+ **溢出次数**。张数 → 属性，星级 → 技能，溢出 → 回收活动。同样**协议待确认** |
| 未拥有却设为使用中 | 不允许；服务端校验，客户端只读 |
| 局内切换 | **不允许**。皮肤在进对局时冻结；局内换皮肤会造成「打到一半换攻击方式」的不一致，也会破坏回放 |

### 6.4.1 重复皮肤怎么变成技能等级（只走这一条）

| 步骤 | 规则 |
| --- | --- |
| 1 | 重复获得皮肤 → 服务端把该皮肤 `leadSkinStar.star` +1，**显示与生效封顶 5**；**不新增任何属性** |
| 2 | 超出 5 星的部分**不丢弃**，累计到该皮肤的「溢出次数」字段（服务端存档），留给后续**皮肤回收活动**折算。客户端只需知道"已满星"，不用处理溢出 |
| 3 | 该皮肤的 `activeSkillId` + 生效星级（1~5）→ 取 `pvpSkillPlan` 中 `skillLevel = 星级` 的那一行（`progressionMode = replace`，高等级整行替换低等级） |
| 4 | 主角技能的**解锁条件**不再是 `unlockHeroLevel`（主角没有英雄等级），而是「该皮肤已拥有」（星级 ≥ 1 即可用） |
| 5 | 入局时把生效星级解析成**最终 `pvpSkillId`** 再冻结进该席位；局内不变，战斗层不知道"星级"这回事 |

> ⚠️ `leadSkinStar` 现有每行的 `desc` 是「最终伤害 +10%」这类**属性**描述，`modify` 也是一串属性改写 id。本版口径下**属性只由皮肤张数给**，所以主角皮肤这几行必须把 `modify` **清空**、`desc` 改成技能描述（如「技能等级 +1 档」）。否则抽到重复皮肤会变成「升星既加属性又升技能」，而且那份属性绕过了 §6.2 的唯一口径。
>
> 🔴 但 `leadSkinStar` 这张表**只用于技能档位**，不要把它当成"属性成长表"来扩展新列——属性成长在 `leadSkinCollect`（§6.4.2），两张表职责不同。

### 6.4.2 收集数量 → 基础属性（唯一分档表）

**新表 `leadSkinCollect`**（列少、行少、策划直接填）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `skinCount` | int | 已拥有主角皮肤的**张数**（去重），主键 |
| `attackRate` | number(%) | 该张数对应的攻击加成 |
| `hpRate` | number(%) | 该张数对应的生命加成 |
| `desc` | string | 展示文本（如「收集 3 张：攻击 +6% / 生命 +6%」） |

示例（**占位，等策划定档**）：

| skinCount | attackRate | hpRate |
| --- | --- | --- |
| 1 | +3% | +3% |
| 2 | +6% | +6% |
| 3 | +9% | +9% |
| 4 | +12% | +12% |
| 5 | +16% | +16% |

规则：

- **按张数取档，不累加**：N=3 就只取第 3 行，**不是** 1+2+3 累加。
- **张数 = 已拥有皮肤的 id 去重数**，与星级、重复次数、使用中皮肤全部无关。所以「抽到重复」既不涨张数，也不改属性。
- 表里缺 N 时，**回落不超过 N 的最大档**（容错）；N=0 按 0 处理（无皮肤 = 无加成，不查表）。
- 属性项一期只做 **攻击 + 生命**（`IZCBattleRates` 现成两个字段）。若后续要加移速/攻速/暴击，**加列**即可，不要改公式结构（§9-7、§9-19）。
- 客户端算法：`N = 已拥有 id 去重数` → 查表 → `unitRates[owner]['1001'] = { attackRate, hpRate }`（与天赋相乘，见 §6.2）。

### 6.5 本期明确不做

- 主角多个技能（每张皮肤只做 **1 个**技能）。
- 主角职业 / 职业克制（明确不存在，别加）。
- **皮肤升星给属性**（明确不做：升星只升技能，属性只由张数给）。
- **皮肤回收 / 溢出兑换活动**（本期只把溢出次数存下来，活动后续再开）。
- 超过 5 星后的继续强化（封顶 5 档）。
- 玩家手动操控 / 指令。
- 主角独立装备、星级、进阶。
- 主城内单独的主角展示位（皮肤切换入口放角色页，不在战斗内）。
- 局内切换皮肤。

### 7.3 `pvpSkill` + `pvpSkillBinding`：每条皮肤 1 条普攻 + 1 个技能

**普攻行（每张皮肤一条）**：`pvpSkill.mode` 决定近战 / 远程。现成可复用：

| 用途 | 现成 skillId | mode | 说明 |

> 🔴 这里只有「**近战 / 远程**（攻击方式）」这一条区分，**没有职业**。不要为了皮肤新增 `warrior / archer / swordsman` 之类的职业字段、枚举、克制关系 —— 主角全皮肤共用同一套属性计算与索敌评分。

**主角技能（每张皮肤 1 个）**：`pvpSkill` 新增行（`skillId` 自定义段）+ `pvpSkillBinding` 绑到 `targetUnitId = 1001`，触发方式按现有 `trigger` 二选一（`every_n_attacks` / `every_seconds`）。

**技能等级 = 皮肤重复度，档位表走 `pvpSkillPlan`。**

| 环节 | 取值 | 说明 |
| --- | --- | --- |
| 当前档位 | `leadSkinStar.star`（该皮肤重复次数 → 星级，**生效封顶 5**） | 抽到重复皮肤 = 星 +1；首张 = 1 星；超 5 星的次数记「溢出」，等回收活动 |

| 解锁条件 | **该皮肤已拥有**（星 ≥ 1） | 🔴 不是 `unlockHeroLevel`（那是英雄等级门），主角技能与英雄等级无关 |

### 8.4 养成与皮肤

**核心：皮肤是「按席位」的，不能全局改 1001 的定义。** `compileZCMatchRuntime` 已经按 `ZC_OWNER_ORDER` 生成 `effectiveDefinitions[owner]`（`ZCMatchRuntimeCompiler.ts:46`），所以只需在编译时给每个席位叠加一份 profile 覆盖即可，4 人局各自皮肤互不影响。

| --- | --- | --- |
| `model/ZCMatchConfig.ts` | `ZCMatchConfig` 新增 `unitProfiles?: Partial<Record<ZCOwner, Readonly<Record<string, IZCUnitProfileOverride>>>>`<br>`IZCUnitProfileOverride = { attackProfile?, attackRange?, attackInterval?, activeSkillId? }` | `activeSkillId` 填的是**已查好档的最终 `pvpSkillId`**；血量/攻击/移速仍走 `ownerRates` / `unitRates` |

**主角技能按皮肤注入**：技能不能只靠 `pvpSkillBinding`（`targetUnitId` 固定 1001，各皮肤会互相覆盖）。两种可行做法，二选一：

1. 复用构筑通道：把「皮肤 → 该皮肤当前档位的 `pvpSkillId`」编译进该席位的 `modifiers[owner].skillPlans`（现成 `loadouts.skillPlans` 会进 `skillRuntime`）；
2. 在 `unitProfiles` 里带 `activeSkillId`（**已经查好档的最终 id**，不是原始 `activeSkillId`），编译期补一条该席位专属的 `skillRuntime`。

> 两种做法都要求：**入局前就把「皮肤 `activeSkillId` × 该皮肤 `star` → `pvpSkillPlan.skillLevel` → 最终 `pvpSkillId`」算成单一 id**。不要在 `skillRuntime` 里保留"再查档"的逻辑——战斗层不读全局表，也不该知道星级存在。

> ⚠️ 分层红线：`zcds/model` 不许 import `role/*`（会带进 cc）。天赋/皮肤数值必须在**入局配置阶段**（`application/ZCClientCombatConfig` 或更外层）算好，以 `unitRates`（倍率）/ `skillModifierIds`（修改器 id）这种纯数据传进战斗。

## 10. 风险与坑（程序必读）

1. **主角有自己的卡行与 unitId（1001），养成数据源是另一个 id（66014）**：两者靠 `captainTalentArmyId` 关联。
   - 1001 行的 `enabled` 必须是 **0**：填 1 会进 `fallbackDeck`，主角变成可上阵卡；
   - 1001 行的 `type` 不能是 **5**：`cards.find(isHqCard)` 取第一行 type=5，1001 排在 2002 前会被误认成主城；
   - 天赋/皮肤拿 1001 去查 ⇒ `armyLevel` / `leadSkin` 里没有这行，**结果全 0 且不报错**；
   - `unitRates` 的 key 必须是 **1001**（战场 unitId），不是 66014。
2. **`card.cycleSeconds` 对主城是 `goldDigTime`（6 秒）**，不是 `soilderAddTime`。主角重产间隔只能从**主城行的 `soilderAddTime`** 直接读，别借 `cycleSeconds`；用错就变成"主角每 6 秒复活"，表面完全正常。
3. **拆行后《建筑卡 unitId 必空》的假设不再被打破**：1001 是独立的 type=2 行，主城只是引用它。但 `findUnplayableDeckCards` 用 `unitId == null` 认建筑卡这条逻辑仍在 —— 别反过来把 `unit*` 数值又内联回主城行。
4. **坐标口径**：`combatDistanceScale = 0.3`（表值 ≈ 世界 px × 3.33）；视图行距又是逻辑行距的 2.14 倍。三个数别混。
5. **不要用通用 `acquire` 每帧重锁**，也**不要调 `refreshPriorityTarget`** —— 两者都会破坏"战斗中不换目标"。
6. **追击无上限 ≠ 用通用 chase 逻辑**：通用分支有 `CHASE_MAX_SECONDS(5s)` / `CHASE_MAX_DISTANCE(3 格)`，主角必须绕开。
7. **天赋/皮肤数值必须在入局时冻结**（天赋 → `skillModifierIds`，张数 → `unitRates`）：战斗中读全局表会破坏回放与多端一致，也违反 `zcds/model` 不依赖 cc 的分层。
8. **三条线必须各走各的输入**（最容易在这里写错）：
   - **属性 ← 皮肤张数**（id 去重计数），查 `leadSkinCollect` 取档，**按档取不累加**；
   - **技能 ← 该皮肤星级**（重复次数，封顶 5）；
   - **打法 ← 使用中皮肤**（零属性收益、也不改技能档位）。
   任何一个交叉（比如"用星级算属性"、"把张数乘到技能上"）都是 bug。
9. **收集加成不是「每张皮肤一个值」**：之前设想的 `armySkin.collectAttackRate` 已废弃。属性只跟张数有关，若按皮肤配值，策划会按品质调，玩家的最优解变成"只抽高品质皮肤"，与口径不符。
10. **`star` 封顶 5 会丢信息**：如果服务端只存 1~5，超出的重复次数就丢了，后续回收活动无法补给老玩家。必须**另存「溢出次数」**（§9-20）。
11. **皮肤不能全局改 1001 的定义**：4 人局各席位皮肤可能不同，必须走 `unitProfiles[owner][unitId]` 按席位覆盖；直接改 `config.units` 会让所有人跟着变，且后加入的一方覆盖前面。
12. **`pvpSkillBinding.targetUnitId` 固定 1001，无法区分皮肤**：不同皮肤的技能必须按席位注入（`skillPlans` / `unitProfiles`），否则 4 人局技能互相覆盖。
13. **主角没有职业**：皮肤之间只差「攻击方式（近战 / 远程）+ 射程 + 间隔 + 技能」，实现看 `pvpSkill.mode` 与这三列数值。不要新增 `warrior / archer` 之类职业枚举或克制表 —— 一加，表现层、AI、索敌、结算会各多一条分支。
14. **`leadSkinStar.modify` 不清空 ⇒ 升星双份收益**：`modify` 原是为"皮肤升星加属性"设计的，本版把它改作"技能档位"。若留着 `modify`，抽到重复皮肤会同时加属性（且绕过 §6.2 的入账口径）和升技能，数值会失控。
15. **技能档位要在入局时算好**：`star` → `pvpSkillPlan.skillLevel` → `pvpSkillId` 的取值必须在配置阶段完成并冻结，不要在战斗中读全局表（同第 7 条）。
16. **随机必须用局内种子**（`this.random`）。
17. **锚点判定用 `owner + building !== 'none' + hp > 0`**（建筑被拆后 `owner` 会改成攻击方）。
18. **快照字段漏还原**：读档后主角变普通单位（原地不动、永远不索敌），线上难复现。

## 11. 建议的实施顺序

1. **P0 产出骨架**：`soldierAddSeconds` 解析 + `tickCaptains`（开局立即产 + 30s 重产）+ 记账 + 死亡清零计时器。
2. **P1 巡逻**：锚点 + 圆内随机采样 + 到点停留 + 圈外兜底。
3. **P2 战斗**：带半径索敌 + 锁定 + 出手 + **无上限追击** + 目标失效回圈。
4. **P3 锚点与收尾**：主城被毁重锚、全无建筑自由巡逻、快照还原、结算剔除、表现标识、测试。
