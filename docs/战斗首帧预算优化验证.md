## 修改与架构边界

| 文件 | 本轮变化 |
| --- | --- |
| `assets/script/app/session/AppSessionAssetService.ts` | 两个预下载worker不再逐项等待解析；解析仍为已有单通道，下载和解析都收尾后才释放预热作用域 |

| `assets/script/app/zcds/view/ZCGameRenderWorld.ts` | 补载数组变化时显式更新已有地块；新建地块取最新帧，同一数组不重复写入 |
| `assets/script/app/zcds/view/ZCNeutralRewardFx.ts` | 显式接收神器爆炸帧，已有事件不重启时间轴，也不为过去事件补播 |

资源经AssetService和原有Scope进入，延迟任务每次await后仍检查取消。缓存64条、根加载4路、后台下载2路、解析1路、核心外壳保留8项保持。无规则、随机源、阵容、协议、Prefab或资产尺寸改动。

## 排查依据

原worker在下载一个根资源后await解析，再下载下一项；两个worker遇到慢Prefab时，下载也一同停住。新回归测试将第一项解析挂起，验证第三项文件仍会下载，而warmup必须等待解析链收尾。

本机Creator3.8.8 SDK中`preload`预设为`maxConcurrency=6,maxRequestsPerFrame=2`。共享downloader的下一轮队列派发捕获触发请求的限制；因此预下载仍在途时，后来的高优先级前台请求可能继续受到低速节奏影响。`preloadAny(...,{preset:'default'},...)`依然走fetchPipeline，跳过的是预下载预设限速，仍不反序列化资产；request中的低priority覆盖default预设priority。

实际19单位对照实验：仅调整前台预算或让单位优先未改善，没有采用。标准预下载预设使2.5秒静默窗口完成21项、保留8核心，随后首帧资源约1632ms；修正前同类资源探针约4581ms、仅完成2项。更早的整轮前置样本为8901ms/1项。它们是单次SwiftShader样本，不换算为稳定提速百分比。
