## 0. 这次改了什么，为什么

旧实现只把 `remoteRef` 当**远程 Asset Bundle** 加载。Asset Bundle 能带资源和数据，
**带不动代码** —— `ZCGameHUDView.ts`、棋盘动画这些编译进 `src/chunks/*.js` 的逻辑，
Bundle 方案连碰都碰不到。

要热更脚本，必须换成官方方案：对原生构建目录里的 `src` + `assets` + `jsb-adapter`
做**文件级 Manifest**，用 `native.AssetsManager` 逐文件比对 md5 下载差异，
再把缓存目录前置到 `FileUtils` 搜索路径。**代价是必须重启游戏才生效**
（新脚本需要干净 JS 环境，Bundle 配置也要重新读取）。

| | 旧：远程 Asset Bundle（v1） | 新：官方全构建目录（v2） |
| --- | --- | --- |
| 清单 | `latest.json` + `manifest.json`（Bundle 列表） | `latest.json`(v2) + `project.manifest` + `version.manifest`(**文件表**) |
| 能更脚本吗 |  只能资源和数据 | ✅ `src/chunks/*.js` 也算文件，一样被替换 |
| 谁做差异比对 | Creator 的 Bundle 版本号（粗粒度，整包） | **引擎逐文件 md5**（细粒度，只下改动文件） |
| 断点续传 | 平台缓存自己管 | 引擎负责，**文件级 + 字节级**，3.6 起原生支持 |
| 生效方式 | 立刻 | **重启游戏** |
| 支持平台 | 原生 + 小游戏 | **仅原生**（官方明确 Web 不用 AssetsManager） |

`remoteRef` 那条远程 Bundle 路径**代码保留、未删除**：它解决的是**包体**（小游戏主包 4 MB 上限），
和原生脚本热更是两件事。目前 `hot_update.json` 的 `enabledPlatforms` 只开 `android/ios`，
原生已改走 AssetsManager，所以 Bundle 路径实际处于"待小游戏接入"的休眠状态。

## 1. 总体结构

```
① 构建（Creator + extensions/hot-update）

   ├── src/{chunks,cocos-js,settings.json,import-map.json,…}   ┐
   ├── assets/{internal,main,remoteRef,resources}              ├ 这三块进清单
   └── jsb-adapter/{jsb-builtin.js,engine-adapter.js}          ┘

② 发布（tools/hotupdate/publish_hotupdate.py + dufs）
   <publish_root>/hotupdate/android/                 （dufs 默认服务 D:\Share）
   ├── 20260918-190000-android/          ← 不可变 release：完整 src/assets/jsb-adapter
   │   ├── project.manifest              （packageUrl 指向本目录，remote* 指向渠道）
   │   ├── version.manifest
   │   ├── release-report.json
   │   └── src/ assets/ jsb-adapter/
   └── dev/                              ← 渠道目录（可变指针）
       ├── project.manifest              （与 release 同名文件内容相同）
       ├── version.manifest
       └── latest.json                   ← 控制文件，**最后一步才原子切换**

③ 客户端启动（ProcedureUpdate → NativeHotUpdateRuntime）
   拉 latest.json → 灰度/最低版本/签名 → 引擎 checkUpdate
     ├─ ALREADY_UP_TO_DATE → 直接进登录

                                                     再加载 business 脚本 ⇒ 新代码生效
```

## 2. Manifest 格式（官方口径）

`project.manifest`（`version.manifest` 是它删掉 `assets` / `searchPaths` 后的精简版）：

```json
{
  "packageUrl": "http://192.168.2.156:5000/hotupdate/android/20260918-190000-android/",
  "remoteManifestUrl": "http://192.168.2.156:5000/hotupdate/android/dev/project.manifest",
  "remoteVersionUrl": "http://192.168.2.156:5000/hotupdate/android/dev/version.manifest",
  "version": "20260918-190000-android",
  "assets": {
    "src/chunks/xxxx.js": { "size": 12345, "md5": "…32 位…" },
    "assets/main/index.js": { "size": 678, "md5": "…" },
    "jsb-adapter/jsb-builtin.js": { "size": 170485, "md5": "…" }
  },
  "searchPaths": []
}
```

要点：

- **`assets` 的 key 是相对构建数据根目录的路径**（`src/…`、`assets/…`、`jsb-adapter/…`），
  `packageUrl + key` 就是下载地址。
- **`main.js` / `application.js` 故意不入清单**：它们必须在热更生效之前就恢复搜索路径，
  一旦被替换会自锁。
- **`version.manifest` 只放主版本**，客户端先拿它判"值不值得下大清单"，省流量。
- `searchPaths` 保持空数组；真正前置的缓存目录由客户端在 `UPDATE_FINISHED` 时写。

生成器：`tools/hotupdate/hotupdate_manifest.js`（Node 标准库，无依赖）。
**构建扩展与发布脚本共用它**，避免两边算法漂移 —— 一旦漂移，差异比对会整包重下。

## 3. 客户端实现

### 3.1 启动链

```
Root.scene → ProcedureBootstrap.onLoad() → navigate(GameRoute.Update) → ProcedureUpdate
   ├─ 平台 = android/ios → createNativeHotUpdateRuntime()   ← 官方 AssetsManager
   └─ 其他平台            → createCocosHotUpdateManager()     ← 旧 Bundle 路径（休眠）
```

`ProcedureUpdate` 现在是薄壳：只负责显示进度与重试，判断逻辑全在
`platform/hotupdate/NativeHotUpdateRuntime.ts`，纯函数部分在 `core/update/`，都可单测。

### 3.2 main.js 注入（唯一让脚本生效的开关）

`extensions/hot-update/builder/hook.js` 在构建后把下面这段放到 `main.js` **最前面**
（必须在 `System.import('./application.js')` 之前）：

```js
(function () {
    var g = typeof window === 'object' && window ? window : (typeof globalThis === 'object' ? globalThis : null);
    if (!g || typeof g.jsb !== 'object' || !g.jsb || !g.jsb.fileUtils) return;
    var storage = g.localStorage || (g.sys && g.sys.localStorage);
    if (!storage) return;
    var hotUpdateSearchPaths = storage.getItem('HotUpdateSearchPaths');
    if (!hotUpdateSearchPaths) return;
    var paths = JSON.parse(hotUpdateSearchPaths);
    g.jsb.fileUtils.setSearchPaths(paths);

    // 上次更新中断在 _temp/ 里：把它恢复进正式缓存目录
    var fileList = [];
    var storagePath = paths[0] || '';
    var tempPath = storagePath + '_temp/';
    var baseOffset = tempPath.length;
    if (g.jsb.fileUtils.isDirectoryExist(tempPath) && !g.jsb.fileUtils.isFileExist(tempPath + 'project.manifest.temp')) {
        g.jsb.fileUtils.listFilesRecursively(tempPath, fileList);
        fileList.forEach(function (srcPath) {
            var relativePath = srcPath.substr(baseOffset);
            var dstPath = storagePath + relativePath;
            if (srcPath.charAt(srcPath.length - 1) === '/') { g.jsb.fileUtils.createDirectory(dstPath); }
            else {
                if (g.jsb.fileUtils.isFileExist(dstPath)) { g.jsb.fileUtils.removeFile(dstPath); }
                g.jsb.fileUtils.renameFile(srcPath, dstPath);
            }
        });
        g.jsb.fileUtils.removeDirectory(tempPath);
    }
})();
```

`localStorage` 的键名 `HotUpdateSearchPaths` 必须与 `NativeHotUpdateHost.ts` 里写入时一致，
改名会直接导致热更静默失效。

### 3.3 版本比较（容易踩的坑）

`AssetsManager` 用同一个比较函数做两件事：**判断远端是否比本地新**，以及
**本地缓存 manifest 与包内 manifest 谁更新**。所以比较必须是**全序**的。

- 项目用 `releaseId` 当主版本，格式 **`YYYYMMDD-HHMMSS-<platform>`**，
  发布脚本会强制校验这个格式（`compareReleaseVersion()` 取时间戳前缀比大小）。
- 这样"包内 < 已缓存 < 远端新版本"单调可比：**已是最新时不会每次启动全量重下**。
- **三份清单的 `version` 别混**：
  - release 与渠道 `project.manifest` / `version.manifest` → `releaseId`；
  - **随包**（写进构建 `data/` 的那份）→ **`clientVersion`**（生成器 `--local-version`，
    发布脚本传 `--client-version`）。它描述的是"打进安装包的那份内容"，不是"远端某个 release"，
    所以不要把 releaseId 泄进包里 —— 构建扩展 `hook.js` 与发布脚本现在写的是同一个值。
  - 两侧都走同一套全序比较，实测 `compareReleaseVersion('0.6.0.0', '20260918-193000-android') = -1`
    （远端更新，正常进文件级比对，内容一致时下载量为 0）。
- 配置项 `nativeVersionCompare`：默认 `release-stamp`；设成 `strict` 则交回引擎默认语义
  （只有远端主版本更大才更新，不支持服务端回滚）。

> 不要用"不相等就返回 1"这种糊法：那样缓存与包内清单的判定会飘，
> 运气不好时每次启动都重下全量。

### 3.4 搜索路径与重启

`UPDATE_FINISHED` 时：

```ts
const merged = prependSearchPaths(host.readSearchPaths(), hotPaths); // hotPaths 至少含缓存目录
host.applySearchPaths(merged);      // jsb.fileUtils.setSearchPaths
host.persistSearchPaths(merged);    // localStorage['HotUpdateSearchPaths']
host.restartGame(1200);             // game.restart()
```

缓存目录固定以 `/` 结尾（与引擎内部 `_temp/` 约定一致）。
若引擎版本差异导致清单 `getSearchPaths()` 返回空，代码会直接用缓存目录兜底。

### 3.5 缓存目录与清理

- 缓存目录：`<应用可写目录>/hotupdate-<channel>/`（`nativeStorageDir` 可覆盖），按渠道隔离。
- **大版本升级清缓存**：`localStorage` 记 `hotupdate.clientVersion`，一旦与配置里的
  `clientVersion` 不同，就删掉整个缓存目录并清掉待恢复标记。
  这是官方"迭代升级"章节的建议 —— 引擎版本变了而 C++ 底层没变，旧缓存会盖住新包。

### 3.6 失败处理

| 场景 | 行为 |
| --- | --- |
| 引擎的更新/解压/校验失败 | 状态 `failed`，**保留已下载分片**，状态文字提示"点击重试" |
| 用户点击重试 | `NativeHotUpdateRuntime.retryFailedAssets()` → 引擎 `downloadFailedAssets()`，**只重下失败项** |
| `latest.json` 拿不到 | 退回"随包清单自举"（包内清单里就写着渠道地址），官方流程本身能跑；`requireRemoteOnFirstInstall=true` 时才阻断 |
| 未进入灰度 | 状态 `deferred`，继续用当前包内/缓存版本，不下载 |
| 客户端低于 `minClientVersion` | 状态 `mandatory-client-update`，阻断进入，提示整包升级 |
| 找不到随包 `project.manifest` | 明确失败并说明原因（多半是构建扩展没跑），**不静默降级** |
| `_temp/` 里有上次中断的残留 | 下次启动由 `main.js` 注入片段搬进正式缓存目录后再更新 |

### 3.7 下载后 md5 校验

引擎不提供纯 JS 的 md5。正式环境把实现挂到
`globalThis.__CITY1001_HOT_UPDATE_MD5__ = (filePath) => md5hex` 即可自动生效；
没有桥时只能放行并记日志（与官方范例一致 —— **校验不了不能假装校验过了**，上线前必须补）。

## 4. 限制（官方明确，别抱幻想）

1. **只用于 Android / iOS**。Web 直接部署，不用 `native.AssetsManager`。
2. **构建时不要开 MD5 Cache**。本项目 android 构建已默认 `md5Cache: false`；
   扩展会告警，发布脚本会再拦一次。
3. **引擎版本或 C++ 原生代码变化必须发整包**。`src/cocos-js/cc.js` 变了但安装包里的
   C++ 底层没变，混跑会出严重问题。客户端已用"客户端版本变化即清缓存"兜底，但发整包才是正解。
4. **必须重启游戏**才生效（新脚本要干净 JS 环境，Bundle 配置要重读）。
5. **服务端保存完整版本**（本次 release ≈ 98 MB / 2361 个文件）。
   好处是天然支持跨版本更新（A → C 直接下差异），不需要逐版本补丁包。
6. Manifest 生成的随机顺序会影响 `md5` 之外的可比性 —— 生成器对目录项排序，
   保证同一份产物多次生成结果**逐字节一致**。

## 5. 构建与发布

### 5.0 前置：构建扩展必须**真的跑起来**（否则全链路白做）

构建扩展负责两件**只能在这一步做**的事：注入 `main.js` 恢复片段、写随包 `project.manifest`。
装进 `extensions/` 不等于生效，要过三关：

1. 编辑器**加载**了它 —— 新装 / 改过之后必须**重启编辑器**（主进程脚本只在启动时加载）；
2. 扩展管理器里**启用**：扩展 → 扩展管理器 → 项目 → `hot-update`，必要时点「重新载入」；
3. `hooks` 路径解析到真文件 —— **基准是 `dirname(contributions.builder)`，不是扩展根目录**。
   端点必须写目录形式 `"builder": "./builder"` 配 `hooks: './builder/hook.js'`
   （与官方 hot-update 范例逐字一致）。写成文件形式 `"./builder/index.js"` 会解析到不存在的
   `builder/builder/hook.js`，**构建照样成功、日志零报错**，只是扩展从不执行。
   守卫用例：`tests/test_publish_hotupdate.py::test_build_extension_hooks_resolve_under_any_base`。

**自证信号**（构建日志里没有第一行就不用往下查业务逻辑）：

```
[hot-update] 构建钩子已载入（hook.js 被构建进程 require 成功）
[hot-update] 已注入搜索路径恢复片段：build/android/data/main.js
[hot-update] 已生成随包 project.manifest：2361 个文件 / 102886503 字节 / 版本 0.6.0.0
```

发布脚本还会兜一次：发现产物里缺注入片段或随包清单时打一整屏告警
（`warn_if_build_extension_skipped`）——因为脚本自己会把这两样补进构建目录，
**很容易把「构建时扩展没跑」这件事盖住**，而安装包里那份是补不进去的。

### 5.1 一键打包发布（BAT 入口 + Python 实现）

热更新这套工具统一收在 **`tools/hotupdate/`** 下（曾散在 `tools/` 顶层）：

| 文件 | 角色 |
| --- | --- |
| `publish_hotupdate.py` | 发布实现（8 步，见下） |
| `publish_hotupdate.bat` | 唯一入口（纯 ASCII 编排层） |
| `hotupdate_manifest.js` | 清单生成器，**构建扩展与本脚本共用** |
| `verify_apk_contents.py` | APK 独立核对（不开工程模块，自己算 md5） |
| `build_hotupdate.mjs` | 旧 Bundle 清单生成器（小游戏路径） |

> **挪动这些文件必须同步改 3 处功能性引用**，漏改不报错、只静默失效：
> py 模块级 `PROJECT_ROOT`（`parents[2]`）、bat 的 `%~dp0..\..`、
> `extensions/hot-update/builder/hook.js` 里 require 清单库的路径
> （**必须写成相对说明符** `../../../tools/hotupdate/hotupdate_manifest.js` ——
> 构建进程的 require 不认跨目录绝对路径，见 `extensions/hot-update/README.md`）。
>
> 另一处独立的坑：`hook.js` 加载清单生成器时如果只走绝对路径，**注入会成功、清单却生成不了**
> （日志只说「无法加载清单生成器」，`error.message` 还是空的），成品表现就是包内少一份
> `project.manifest`。现在走「**读源码求值 → 相对说明符 → `createRequire`**」三层兜底。
> 该差异原生 node 测不出，靠 `tests/smoke_hotupdate_hook.mjs` 里 patch `Module.prototype.require`
> 造出「绝对路径被拒」的场景来守。
>
> ⚠️ 还有一条容易误判的：**改过 `extensions/hot-update/` 下任何文件都必须重启编辑器**，
> 构建进程跑的是编辑器启动时加载的内存副本。实测 14:13 改 `hook.js`、14:17 重新构建，
> 日志里报的还是改前那三行 —— 看起来像"改了没用"。`hook.js` 现在会打版本指纹
> （`…require 成功，rev 2026-09-28.2`），指纹没变就别查业务逻辑。
> 其余是文本引用（`package.json`、测试、本文档、扩展 README）。
> 回归测试 `test_tooling_sits_under_tools_hotupdate_and_root_derivation_holds` 会拦住层级数写错。

`tools\hotupdate\publish_hotupdate.bat` 是唯一入口：**双击走交互菜单，带参数则直接执行**。

| 命令 | 作用 |
| --- | --- |
| `tools\hotupdate\publish_hotupdate.bat` | 双击（无参数）：预检 + 菜单 + 确认（菜单里会单独问一次 APK） |
| `tools\hotupdate\publish_hotupdate.bat android` | 构建 + 发布 android（有 gradle 工程时会连 APK 一起编） |
| `tools\hotupdate\publish_hotupdate.bat android --no-apk` | 只要热更包，不编 APK |
| `tools\hotupdate\publish_hotupdate.bat android --skip-build` | 复用现有产物，只发布（APK 仍会编译） |
| `tools\hotupdate\publish_hotupdate.bat ios --channel test` | 其余参数原样透传给 python |
| `tools\hotupdate\publish_hotupdate.bat --help` | 完整参数（python argparse 输出） |

双击后的菜单**先预检再让人确认**，避免"顺手发错渠道"：

```
  编辑器        ：正在运行
                  （命令行构建会与编辑器抢工程，智能模式因此改为复用现有产物）
  静态服务器    ：在监听，发布后有 HTTP 校验
  [1] Android 智能模式（推荐）：编辑器开着就复用现有产物，没开就先构建
  [2] Android 强制重新构建后再发布
  [3] Android 仅发布，复用 build 目录里现有产物
  [4] iOS 智能模式
  [0] 退出
```

选完之后打印计划并要求回车确认。计划里有三样是刻意放的：
**现有产物的时间戳**（复用模式最怕发错那一份）、发布根目录**剩余空间**与已有 release 数量
（一份约 100 MB，磁盘满会以"复制失败"的形式挂掉，很难归因）、本次 release-id。

实现上 bat 只做编排（找 python / node、拆自己的开关、透传、暂停、回传退出码），
预检与中文交互都在 `publish_hotupdate.py --interactive` 里 —— 原因见下面这一节。

脚本 8 步：

```
[1/8] Creator 构建（platform=<p>;debug=false;md5Cache=false）
[2/8] 定位构建数据根目录（含 main.js 与 src/ 的那一层）
[3/8] 注入 / 校验 main.js 恢复片段（幂等，--skip-build 复用别人产物时的兜底）
[4/8] 生成官方清单（src + assets + jsb-adapter 逐文件 md5）
[5/8] 编译 APK（gradle assembleRelease；必须排在 3、4 之后，见 5.1.2）
[6/8] 发布不可变 Release（完整构建目录 + 两份清单 + 报告）
[7/8] 写渠道控制文件，最后原子切换 latest.json
[8/8] HTTP 校验（latest.json / 两个清单的 sha256 必须对得上）
```

工程正在 Creator 中打开时，先在编辑器里构建，再 `--skip-build`。

Python 可脱离 BAT 单独跑（CI 或其它工程复用）：

```bash
python tools/hotupdate/publish_hotupdate.py android --skip-build \
  --publish-root D:\Share \
  --base-url http://192.168.2.156:5000/hotupdate \
  --channel dev --rollout 10
```

可覆盖：`--release-id --channel --client-version --rollout --creator --build-dir
--node --http-timeout --no-http-check --interactive
--apk/--no-apk --apk-variant --apk-out --gradle-jdk --gradle-arg --gradle-timeout
--android-sdk --keystore --store-password --key-alias --key-password`。

#### 5.1.1 bat 必须保持纯 ASCII（踩坑记录）

**bat 里不要写中文，中文一律放 `publish_hotupdate.py`。** 两条都是实测撞出来的：

1. **非 ASCII 会让 cmd 吞掉半行。** cmd 是按字节 + 当前代码页解析 bat 的，`goto`
   跳标签时会落在多字节字符中间，半行被当成命令执行，于是报出
   `'lish_hotupdate.bat' is not recognized as an internal or external command`
   这种和真实原因毫无关系的错。UTF-8（带 BOM / 不带 BOM）与 GBK 三种写法配 CRLF
   **都会踩**；把同一份文件的非 ASCII 全替换成 `*` 后一次干净通过 —— 这就是判据。
   Python 侧编码是可控的：bat 里 `chcp 65001` + `PYTHONIOENCODING=utf-8`。
2. **`shift` 会把 `%0` 一起移掉。** 参数解析循环跑过 `shift` 之后，`%~dp0` 变成了
   第一个参数的目录，`"%~dp0publish_hotupdate.py"` 于是指向工程根。症状很迷惑：
   **双击（无参数）能用，带参数就找不到脚本**。所以 `%~dp0` 必须在解析前存进
   `PUBLISH_PY` 变量再用。

两条都有守卫用例：`test_bat_entry_is_ascii_only`（同时断言"`%~dp0` 不得出现在首次
`shift` 之后"）与 `test_bat_double_click_menu_cancels_cleanly`。

### 5.2 APK 与热更包一起出

一次运行同时产出两样东西：**安装包（APK）** 与 **热更 release 树**，两者内容同源。

**为什么必须同源。** Creator 生成的 gradle 工程把构建目录直接当作 APK 的 assets
（`native/engine/android/app/build.gradle` 里的 `assets.srcDir "${RES_PATH}/data"`，
且 `build/android/assets` 是指向 `data/` 的符号链接）。所以：

```
[3/8] 注入 main.js  ─┐
[4/8] 随包清单      ─┴─→  改的就是 <build_dir>/data/  ─→ [5/8] gradle 把它打进 APK
```

**顺序不能换**：APK 先编的话，包里那份 `main.js` 是旧的 —— 装到机器上
「资源能下载、脚本永不生效」，而且构建全程零报错。这也是为什么 APK 步骤一定在
注入与清单之后。

编完之后 `tools/hotupdate/verify_apk_contents.py` 会独立核对（不复用发布脚本任何函数）：
APK 里 `assets/project.manifest` 的版本是 `clientVersion` 而非 `releaseId`、
`assets/main.js` 含注入标记、清单里每个文件的 md5 与 APK 内对应条目一致。

#### 5.2.1 JDK 必须是 17（官方口径）

| 来源 | 要求 |
| --- | --- |
| Cocos 官方《v3.8 Android 工程升级》 | 「由于 Android Gradle 插件的要求，开发者需要将 **JDK 升级到 17**」 |
| AGP 8.10.0 发布说明兼容性表 | JDK 最低 **17** / 默认 **17** |
| Android 官方《Java versions in Android builds》 | 「Android Gradle Plugin version 8.x **requires JDK 17**」 |
| 本工程 `native/engine/android/build.gradle` | AGP **8.10.1**；`gradle-wrapper.properties` 为 Gradle **8.11.1** |

**JDK 11 不行**（那是 Creator 3.7 之前 AGP 4.1/7.x 时代的事，网上有些文章还在传，
以官方升级文档为准）。用错版本时 gradle 会报
`Android Gradle plugin requires Java 17 to run. You are currently using Java 11.`
——不会报成"版本不对"，很容易误判。

脚本因此做了三件事：

1. 启动前就探测 JDK，**低于 17 直接拒绝**（`GRADLE_MIN_JDK`），
   避免 Creator 白构建一轮才失败；
2. 运行时**显式覆盖子进程的 `JAVA_HOME`** —— 本机 `JAVA_HOME` 指向
   `corretto-1.8.0_502`（JDK 8），不覆盖的话 gradle 会跟着它启动然后加载 AGP 失败；
3. `--gradle-jdk` 是**硬约束**：显式指定了却不可用就报错，不偷偷换一个，
   否则「以为用的是 17」和「实际用的是别的」会悄悄错开。

JDK 解析顺序：`--gradle-jdk` → `HOTUPDATE_GRADLE_JDK`/`GRADLE_JDK` →
`JAVA_HOME` → 常见安装路径（`C:\Program Files\Java\jdk-*`、`%USERPROFILE%\.jdks\*`、
Android Studio 的 `jbr`）。本机可用的 17 在 `C:\Program Files\Java\jdk-17.0.4`。

```bat
tools\hotupdate\publish_hotupdate.bat android --gradle-jdk "C:\Program Files\Java\jdk-17.0.4"
```

#### 5.2.2 产物位置与判定

| 项 | 位置 |
| --- | --- |
| APK（归档，带 release-id） | `outputs/apk/<release-id>/<工程名>-<variant>-<release-id>.apk` |
| APK（gradle 原生输出） | `build/android/proj/build/<工程名>/outputs/apk/<variant>/` |
| gradle 完整日志 | `outputs/hotupdate-logs/gradle-<release-id>.log` |
| APK 的 sha256 / 体积 / JDK | release 报告里的 `apk` 段 |

几个刻意的设计：

- **编译前把旧 APK 挪到 `proj/build/_stale-apk/`**（挪走不删）。gradle 的
  up-to-date 判定包含「输出文件是否存在」，挪走后打包任务一定会重跑；
  万一 gradle 这轮失败，旧包也还在。
- **挪走后若又出现一个 APK，mtime 比旧包新才算本次重新打包。** 否则报
  `rebuilt=false` 并把「gradle 判定输入没变、沿用现有产物」打出来 ——
  免得「以为重新编过了，其实用的是上次的包」。
- **找不到 APK 就失败**，不拿旧包充数。这是这条链路最阴的静默故障：
  发布照常成功、APK 也在，但里面是旧代码。
- 归档名带 `<release-id>`，与热更 release 一一对应，便于和线上包对账。

#### 5.2.3 签名与其它 gradle 覆盖

默认沿用 `gradle.properties` 里已有的签名配置（当前工程用的是 Creator 自带的
`debug.keystore`，**正式发版必须换成自己的 keystore**）：

```bat
tools\hotupdate\publish_hotupdate.bat android ^
  --keystore D:\keys\city1001.jks --store-password *** ^
  --key-alias city1001 --key-password ***
```

四个参数会转成 gradle 的 `-PRELEASE_STORE_FILE=...` 覆盖项。
口令里若含 `&`、`|` 等 cmd 特殊字符，改成写进 `gradle.properties`（`-P` 会经 cmd 解析）。

其它：`--apk-variant debug`（默认 release）、`--apk-out <目录>`（改归档位置）、
`--gradle-arg <参数>`（可重复，追加给 gradle）、`--gradle-timeout <秒>`（默认 3600）、
`--android-sdk <目录>`（默认读 `local.properties` 的 `sdk.dir`，其次 `ANDROID_HOME`）。

iOS 走 Xcode 出 IPA，本脚本暂未接入；对 iOS 传 `--apk` 只会打一行提示。

#### 5.2.4 构建扩展没生效的告警，对 APK 更致命

`warn_if_build_extension_skipped()` 那段告警在引入 APK 之后更要紧：脚本会把注入片段
与随包清单补进**构建目录**，所以发布树看着完全正常；但如果构建扩展当时没跑，
**这两样补不进已经打好的 APK**。现在 APK 由同一次运行产出，包内内容与发布树天然一致 ——
前提就是那次 Creator 构建里扩展真的生效了。

### 5.3 dufs 静态服务

`dufs` 保持原样，把 `--publish-root`（默认 `D:\Share`）作为根目录即可，目录结构天然匹配：

```bat
dufs D:\Share -p 5000 --allow-all
```

客户端 `hot_update.json` 的 `latestUrlTemplate` 指向
`http://<开发机局域网IP>:5000/hotupdate/{platform}/{channel}/latest.json`。
手机访问本机服务时**不要**写 `127.0.0.1`，要写局域网 IP。

### 5.4 `latest.json`（schemaVersion = 2）

```json
{
  "schemaVersion": 2,
  "releaseId": "20260918-190000-android",
  "platform": "android",
  "channel": "dev",
  "minClientVersion": "0.6.0.0",
  "createdAt": "2026-09-18T11:00:00Z",
  "packageUrl": "http://…/hotupdate/android/20260918-190000-android/",
  "remoteManifestUrl": "http://…/android/dev/project.manifest",
  "remoteVersionUrl": "http://…/android/dev/version.manifest",
  "projectManifestSha256": "sha256:…",
  "versionManifestSha256": "sha256:…",
  "rolloutPercentage": 100,
  "rolloutSalt": "20260918-190000-android",
  "fileCount": 2361,
  "totalBytes": 102886503
}
```

`schemaVersion: 1`（旧的 Bundle 列表格式）与 v2 互不接受 —— 客户端解析失败会明确报错，
不会把两种口径混用。

### 5.5 发布纪律

1. **先传文件、后切 `latest.json`**：玩家拉到的清单一定对应已存在的文件。
2. **Release 目录不可变**：同名 release-id 二次发布会直接拒绝（本地 staging 和远端目录两道）。
3. **签名后发布**：正式 `latest.json` 必须有 `signature` + `keyId`，
   客户端同步把 `allowUnsignedManifests` 关掉。
4. **回滚**：把 `latest.json` 的 `releaseId` / `packageUrl` / `remote*Url` 指回旧 release。
   客户端按时间戳比较，指回旧版本同样会收敛。

APK 那 6 项用**假 `gradlew.bat`** 驱动（真 gradle 一遍十几分钟，单测跑不起），

| 用例 | 抓的是 |
| --- | --- |
| `test_parse_java_major_handles_legacy_and_modern` | `1.8.0_502` 必须还原成 8，否则会被当成 1 而"通过" JDK 17 校验 |
| `test_builds_apk_alongside_hotfix_release` | 任务名按 `settings.gradle` 的模块名拼、`JAVA_HOME` 被显式覆盖、APK 归档路径、报告里的 sha256 |
| `test_no_apk_flag_skips_gradle_entirely` | `--no-apk` 时**完全不调用 gradle**，报告里 `apk` 为 null |

| `test_stale_apk_is_not_mistaken_for_a_fresh_build` | gradle 报成功但没产出新包时**必须失败**，不拿上次的 APK 充数 |

13 条负项是既有问题（`remoteRef/*.json` 打包格式变更、美术挪目录、地图预设），
与热更新无关，判回归按这个指纹排除。

另外几处冒烟/复核：

```bash
# 1) 构建扩展在临时目录上的注入 + 清单（不碰 build/）
node tests/smoke_hotupdate_hook.mjs                      # 13 项

# 2) 拿**真实构建产物**跑一次完整发布（约 55 秒，产出 ~98MB release 树）
python tools/hotupdate/publish_hotupdate.py android --skip-build \
  --publish-root tmp/pub-real --release-id 20260918-193000-realcheck --no-http-check
# 期望：2361 个文件 / 102886503 字节

# 3) 独立复核（不复用发布脚本任何函数，自己算 md5/sha256）
python tmp/verify_real_release.py                        # 真数据下 42 项

# 4) 连 APK 一起出，再核对 APK 里打进的内容与 release 是否同源
python tools/hotupdate/publish_hotupdate.py android --skip-build --apk \
  --gradle-jdk "C:\Program Files\Java\jdk-17.0.4" \
  --publish-root tmp/pub-apk --release-id <id> --no-http-check
python tools/hotupdate/verify_apk_contents.py --apk <归档的 apk> \
  --release tmp/pub-apk/hotupdate/android/<id> --client-version 0.6.0.0
```

复核脚本查的是发布脚本**自己说自己对了**之外的东西：随机抽 40 个文件重算 md5 + size、
`release 目录文件数 == 清单条目数`（需排除 `main.js` / `application.js` 与三份清单自身）、
`latest.*Sha256` 与文件实际哈希一致、渠道清单与 release 逐字节一致、
**随包清单每个 md5 与远端逐条一致**（算法一旦漂移，每次启动都会全量重下）、
注入片段排在 `// SystemJS support.` 之前。

`verify_apk_contents.py` 同样不 import 发布脚本：直接开 zip 读 APK，
核对 `assets/project.manifest` 的版本是 `clientVersion` 而非 `releaseId`、
它指向渠道目录、文件表与 release 清单一致、`assets/main.js` 含注入标记、
清单里每个文件在 APK 内的 md5 逐条相等，以及 `main.js`/`application.js` 确实不在清单里。

- [ ] gradle 用的是 **JDK 17**（日志里 `Launcher JVM: 17.x`）；本机 `JAVA_HOME`

## 8. 未决 / 已知风险

- **真机未验收**：`NativeHotUpdateHost` 里的 `fullPathForFilename('project.manifest')`
  路径探测在不同引擎小版本上可能返回不同结果，已准备 `getWritablePath()` 与
  `getDefaultResourceRootPath()` 两条兜底，并支持 `localManifestPath` 配置覆盖；
  真机第一件事就是确认这里命中了哪个候选。
- 缓存目录未做体积上限 / LRU（官方也没给），长期多次更新只增不减，
  靠"客户端版本变化清目录"粗粒度兜底。
- **「构建扩展没生效」告警只对某个构建目录的第一次发布准**：发布脚本自己补进去的
  注入片段与随包清单，第二次再看就跟扩展干的一样了。判断依据仍是构建日志里的三行。
- **Creator 的 MCP 无法触发构建**（`project_manage action=build` 只返回
  "Build panel opened, please start build manually"），所以"扩展是否被加载并执行"
  只能人工在编辑器里构建一次来确认。
- `remoteRef` 的 xlsx 配置热更仍走 Bundle 路径，与原生全目录热更并存；
  小游戏接入时再统一。
- `docs/热更新方案.md`（本文）与 `extensions/hot-update/README.md` 有少量重叠。
