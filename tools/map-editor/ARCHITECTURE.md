# 三套地图编辑器 · 体验与架构方案

> 对象：对局地图（`app.js` 3053 行）· 章节领地（`territory-app.js` 1093 行）· 大地图（`bigmap-app.js` 1432 行）
> 共 5578 行 app 代码 + 951 行 `formats/`（几何/校验/UI 已抽）+ 746 行 `server.mjs`。
> 这份文档回答一个问题：**作为前端，接下来该改什么、不该改什么、凭什么**。

---

## 0. 结论先行

1. **重复量没有想象的大**。三套真正共用的横切逻辑只有四样：相机（zoom/pan）· 撤销栈 · 命中测试 · 脏标记，合计约 **400 行**。
   剩下 5000 多行的差异是**领域差异**（连续笔刷 + 镜像 / 站点表单 + 分批 / 世界布局 + chunk），不是排版差异。
2. **所以不要为了"整洁"重写成一个通用编辑器**。那会变成一个可配置化地狱：三个领域的交互模型根本不是一回事。
   真要收口，只收那 400 行的横切件，收益/风险比才成立。
3. **真正会咬人的是「落笔时重复写 DOM」，跟数据规模关系不大**（2026-10-20 实测）：
   - 对局地图**一笔落下去就把整层重画一遍**：220 次 `setAttribute('class')` + 87 个装饰 `<image>`
     销毁重建；60 帧拖动累计 **+3096 / −3096 个节点、7920 次属性写**。
     同样的动作在 `territory-app.js` 里只有 **1 次**属性写 —— 差的是"做没做增量"，不是格数。
   - **撤销快照不是瓶颈**：`JSON.parse(JSON.stringify(map))` 实测 40×40 = **0.057ms**、
     100×100 = **0.276ms**（含快照两次 + 输出序列化），连帧预算的 2% 都不到。§3.2 已否决 op-log。
4. **该做的两件事，都已做完**：① 落笔增量（格子值守卫 + 各层 markup 守卫）→ ② 输出面板延后到
   `endStroke`。对局地图一次编辑 **1.77ms → 0.65ms**，一笔的节点增删 **+87/−87 → +1/−0**，
   60 帧拖动的属性写 **7920 → 196**。**没有 ③** —— 离屏缓存和抽内核都要等 §5 的触发条件。
5. **一句话立场**：瓶颈在**落笔时无脑重写 DOM**，既不在"代码重复"，也不在"撤销粒度"。

## 1. 现状量化

| 文件 | 行数 | 领域特征 | 与外层耦合 |
| --- | --- | --- | --- |
| `app.js`（对局地图） | 3188 | 连续笔刷 + 镜像 + 分区 + 装饰拖动 | `<script src>`（IIFE，无模块） |
| `bigmap-app.js` | 1432 | chunk 渲染 + 实体层 + 半径刷 + 泊松 | `type="module"` |
| `territory-app.js` | 1093 | 站点表单 + 分批校验 + 格式刷 | `type="module"` |
| `formats/hex-grid.js` | 111 | 唯一几何口径 ✅ | 零依赖 |
| `formats/*-format.js` | 667 | 各自校验/归一化 | 纯函数 |
| `formats/ui-kit.js` | 45 | 脏标记/缩放滑块 ✅ | 零依赖 |

**横切重复面**（三套各写一份，语义几乎相同）：

| 能力 | 对局地图 | 领地 | 大地图 | 差异 |
| --- | --- | --- | --- | --- |
| 相机 zoom/pan | `zoom` 0.4~6 + `panX/panY`（viewBox） | `zoom` 0.5~4 + `viewX/viewY`（viewBox） | `zoom` 30~220 + 容器 scroll | 🔴 语义/机制都不同 |
| 命中测试 | `toLocal` + 几何反算 | `cellAtLocal` | `cellAtLocal` | 基本同构 |
| 撤销 | 快照 ×80 | 快照 ×80 | 快照 ×60 | 同构 |
| 脏标记 | `syncDirtyUI` | `setDirty` | `setDirty` | 已收口 |

> 结论：能抽的是「命中 + 撤销 + 脏标记」；**相机抽不了**（一个用 viewBox、一个用容器滚动，硬统一会破坏大地图的滚动条体验）。
>
> 撤销那一栏看着最重复（三份快照栈），但**重复 ≠ 值得抽**：实测三份加起来不到 60 行、调用点各 8 处，
> 抽出去省不到 50 行却要跨三个模块改签名。它不疼，别动它（§3.2）。

## 2. 架构提案（带迁移路径，不是一次性重写）

```
tools/map-editor/
├── core/                    # 零 DOM、可单测
│   ├── hex-grid.js          # ✅ 已有：几何唯一口径
│   ├── hit-test.js          # 【新】cellId ⇄ 坐标反算（把三套的 cellAtLocal 收进来）
│   └── validate-runner.js   # 【新】规则数组 → issues（增量重算受影响格）
├── render/
│   ├── terrain-cache.js     # 【新】地形层离屏缓存（一次性绘制 → 一张位图）
│   └── svg-view.js          # 现有 SVG 渲染调度（chunk / 层 / 只重画变化格）
├── editors/
│   ├── board.js             # 对局地图：只提供 config + 校验 + 序列化
│   ├── territory.js
│   └── bigmap.js
└── formats/                 # ✅ 已有：数据格式与校验
```

**每个 editor 只剩三件事**：
```js
export const config = {
  cells: { resolve: (map, hexId) => ({ terrainClass, entityKind, entityId }) },
  tools: [{ id: 'brush', paint: (ctx, hexId) => ops }],
  validate: (map) => issues,
  serialize: (model) => payload,
};
```
理想状态下每套 300~400 行（现在 1000~3000），但**这是第三步才做的事**。

### 迁移三步（每步都能独立上线 + 独立验证）

| 步 | 内容 | 影响面 | 判据 |
| --- | --- | --- | --- |
| ✅ ① 落笔增量 | 对局地图：hex class 值守卫 + 三层 markup 守卫 + 输出面板延后 | 单文件 | 一笔的 `setAttribute` ≤ 格数的 1/4；60 帧拖动属性写 < 500（实测 196） |
| ✅ ② 输出面板延后 | 笔画期间不刷 ASCII / JSON，`endStroke` 补一次 | 单文件 | 笔画期间输出面板 0 次变更、松手恰好 1 次 |
| ③ 地形离屏缓存 | 大地图先上（格数最多），当前 40×40 未到门槛 | 单文件 | 首次渲染后 DOM 节点数 < 800；编辑一格的重绘 < 8ms |
| ④ 抽 hit-test + 相机 | 把 `cellAtLocal` 收进 core；相机保持各自实现 | 三套各 30 行 | 三套 `hitAt(x,y)` 探针结果一致 |

**不建议一步到位**：三套都在用，一次重写意味着三套同时回归，出问题分不清是新内核还是原逻辑。
③④ 的触发条件见 §5 —— 现在都还没到。

## 3. 四个关键决策

### 3.1 渲染：SVG 还是 Canvas？→ **分档；先做增量，离屏缓存等规模到了再说**

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| A. 纯 SVG（现状） | ≤ 2000 格 | 交互免费（hover/事件/命中），节点多了掉帧 |
| **B. SVG + 地形离屏位图（推荐）** | 2000 ~ 20000 格 | 改 60 行：地形画到 `OffscreenCanvas` → `toDataURL` → 当 `<image>` 垫底，SVG 只保留**被编辑过的格 + 实体** |
| C. 纯 Canvas 2D | > 20000 格 | 命中/hover/文本全要自己实现，等于重写渲染层 |

**推荐 B**。理由：它把"10000 个 path"压成"1 张图 + 几百个节点"，但**不用重写交互**。
判据：`document.querySelectorAll('#board path').length < 800` 即达标。

> C 只有在"格子 > 2 万"或"要实时动画"时才值。现在 100×100 用 B 就够了。

**已落地的三层增量（2026-10-20，对局地图）** —— 这套手法 `territory-app.js` 早就写对了
（`render()` 里"值没变就别写"，注释还标了 `getScreenCTM()` 每次要付 1.7ms 强制布局），
只是没回灌到最大最老的那个文件：

| 修法 | 位置 | 依据 |
| --- | --- | --- |
| hex class 值守卫（内存缓存，不回读 `getAttribute`） | `render()` | 拖动时每帧真变的只有 1~2 格 |
| `freeDecor / resources / mapMetadata` 层 markup 同值守卫 | `drawXxx()` | 照 `drawBackground()` 的既有范式；注释里早就记过"重写会重建 `<image>`，大图重新解码、底图闪一下" |
| 输出面板（ASCII / JSON）延后到 `endStroke` | `syncOutputs()` | 拖动中每帧都 `JSON.stringify(buildJSON(), null, 2)` + 写大段文本，中间态没人看 |

实测（同一套 Playwright 探针，改前 → 改后）：一次编辑 **1.77 → 0.65 ms**；一笔节点增删
**+87/−87 → +1/−0**；60 帧拖动属性写 **7920 → 196**；输出面板笔画期间 **每帧 → 0 次**。

### 3.2 撤销：**保持全量快照**（op-log 已量化否决 · 2026-10-20）

这里原来写的是"改成操作日志（op 平均 100~200 字节、内存 6MB → 几十 KB）"。**量完就撤了**：

| 规模 | `JSON.parse(JSON.stringify(map))` 一次 | 60 步常驻 |
| --- | --- | --- |
| 40×40（25 城 / 20 怪，7.4KB） | **0.057 ms** | ≈ 0.4MB |
| 100×100（74 城 / 60 怪，32KB） | **0.276 ms** | ≈ 2MB |

0.276ms 连一帧预算的 2% 都不到 —— **每次 commit 深拷贝"很贵"这个前提不成立**。
而 op-log 的代价是**每种编辑都要写正/反两个 op，漏一个就是"撤销不干净"**，
这是最难查的一类 bug（三套编辑器 × 每种编辑都要覆盖）。收益 0.2ms、风险一整类 bug，**不做**。

**撤销粒度**那个诉求（"刷了 30 格想只退一步"）不需要 op-log：在 `endStroke` 里按格数
或时间再切一刀就能做到，改动局限在 20 行内。

> 若将来真要上 op-log，唯一的入场条件是"单次 commit 明显超过 2ms"——用
> `performance.now()` 包住 `snapshot()` 量一次，别凭体积估算。

### 3.3 校验：点按钮 → **双轨（即时 lint + 发布权威）**

现状：点「校验」才跑，红环才出现；编辑时不知道有没有引入问题。

| 层 | 时机 | 规则 | 用途 |
| --- | --- | --- | --- |
| 即时 lint | 每次编辑后，**只重算受影响格及其邻居** | 重叠 / 越界 / 连通性 | 红环跟着编辑走 |
| 权威校验 | 保存 / 发布时全量 | 完整规则（含跨表对账） | 挡住脏数据 |

**不要**把全量校验塞进每帧 —— 现在领地一次全量校验 ~10ms，100×100 会到 100ms 级。
增量重算的边界：这次编辑涉及的格 + 1 环邻居（连通性判定只需要局部）。

### 3.4 数据契约：统一中间表示，但**只在内核层用**

三套产物格式不同（对局是 `ascii` 字符画 + 站点数组，领地是 footprint 列表，大地图是布局 JSON）。不要强行统一产物 —— 那会牵动客户端与转表链路。

只在编辑器内核里用一层中间表示：
```ts
interface EditorModel {
  grid: { rows, columns };
  cellProps: Map<hexId, Record<string, unknown>>;   // 地形/分区/候选…
  entities: Entity[];                                // 城/怪/站点/装饰，统一带 footprint
}
```
`serialize()` 负责转回各自格式。**收益**：内核、命中、撤销、框选全部只认这一层。

## 4. 体验优化（按 ROI 排序）

| # | 优化 | 现在 | 为什么值得 | 量级 |
| --- | --- | --- | --- | --- |
| 1 | **撤销粒度对齐直觉** | 拖一笔 = 一步（靠 `endStroke` 手动合并） | 现在"刷了 30 格再撤销"会一次全退，没法精确回退一步 | 小（在 `endStroke` 里再切一刀，不需要 op-log） |
| 2 | **框选 + 批量** | 只能单格点 / 笔刷刷 | 领地把 20 个候选格改成站点，现在要刷 20 次 | 中 |
| 3 | **实时校验红环** | 点「校验」才出 | 画完 100 格才发现重叠，白干 | 中（见 §3.3） |
| 4 | **图层显隐统一** | 只有大地图有 4 个开关 | 大地图能关范围/区块/编号，另两套没有；反过来领地需要"只显示某类站点" | 小 |
| 5 | **悬停就近信息** | 只有坐标 | 领地悬停显示"这个格子属于哪个战斗 id、能放几个基地"，比点开面板快 | 小 |
| 6 | **变更摘要（导出 diff）** | 无 | 策划改完图给程序看差异，现在只能 git diff 大 JSON | 中（要自己算两份快照的差分） |

**不建议做的体验项**：命令面板（Ctrl+K）、主题切换、拖拽排序面板 —— 这些是"看起来高级"，对这三个工具的实际操作频率没有帮助。

## 5. 什么时候才值得动

| 触发条件 | 该做什么 |
| --- | --- |
| 大地图要上真的 100×100 布局（现在只有 40×40） | 先做 §3.1-B 离屏缓存（撤销不用动，见 §3.2） |
| 新增第四套编辑器 | 才值得抽 `core/history` + `core/hit-test`（省 400 行 × 复制度） |
| 单次编辑到 `render` > 16ms（一帧） | 立刻上离屏缓存，不要先优化算法 |
| 单次 `snapshot()` 实测 > 2ms | 才考虑 §3.2 的 op-log；否则先查 `commitUndo` 的 `sameSnapshot` 短路 |

**没到这些条件就继续用现在的结构**。三套都在稳定产出图，为了"架构好看"重写是最差的投入。

## 6. 风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 🔴 共享内核变上帝对象 | 三套差异一旦塞进 `if (kind === 'bigmap')`，内核就废了 | 内核只提供**机制**（相机/历史/命中），**策略**（怎么画、怎么校验）全部留在 editor |
| 🔴 三套同时回归 | 一起改就分不清是谁的问题 | 严格按 §2 逐步走，每步单独验证 + 探针留档 |
| 增量守卫漏写 | "值没变"判断错了，画面就停在旧状态 | 差分判据：`grid` 变了的格 class 必须跟着变、没变的必须不动（三套各一条） |
| 离屏缓存与编辑不同步 | 缓存图脏了，画面就错 | 只缓存"未被编辑过的地形"；编辑过的格永远走 SVG 覆盖层 |
| 对局地图是 IIFE | 抽共享代码抽不到它 | 要么接受它独立（现状），要么单独一次改成 module（风险自担） |

---

## 7. 一句话总结

**这套工具现在缺的不是"更漂亮的架构"，是"在大图上不卡"和"撤销听话"。**
先把这两件做掉（约 150 行改动，可独立验证），再谈抽内核；
真要抽内核，也只抽那 400 行横切件 —— 剩下的 5000 行是三个不同产品，统一它们是负收益。
