# 三套地图编辑器 · 体验与架构方案

> 对象：对局地图（`app.js` 3053 行）· 章节领地（`territory-app.js` 1093 行）· 大地图（`bigmap-app.js` 1432 行）
> 共 5578 行 app 代码 + 951 行 `formats/`（几何/校验/UI 已抽）+ 746 行 `server.mjs`。
> 这份文档回答一个问题：**作为前端，接下来该改什么、不该改什么、凭什么**。

---

## 0. 结论先行

1. **重复量没有想象的大**。三套真正共用的横切逻辑只有四样：相机（zoom/pan）· 撤销栈 · 命中测试 · 脏标记，合计约 **400 行**。
   剩下 5000 多行的差异是**领域差异**（连续笔刷 + 镜像 / 站点表单 + 分批 / 世界布局 + chunk），不是排版差异。
2. **所以不要为了"整洁"重写成一个通用编辑器**。那会变成一个可配置化地狱：三个领域的交互模型根本不是一回事。
   真要收口，只收那 400 行的横切件，收益/风险比才成立。
3. **真正会咬人的是两件事，而且都跟架构整洁无关**：
   - **撤销是 `JSON.parse(JSON.stringify(map))` 全量快照**：现在 40×40 的布局是 11.7KB，
     60 步 ≈ 700KB 还好；**换成 100×100 + 74 座城会到 60~100KB/份 ⇒ 60 步 4~6MB 常驻**，
     而且每次 commit 都要深拷贝 + 序列化一遍。大图上是实打实的卡顿源。
   - **渲染是全量 SVG 节点**：大地图 100×100 = 10000 个 `<path>`，现在靠 chunk 懒建压到 ~4000，仍然偏高。
4. **该做的顺序**：① 撤销改 patch（成本最低、收益最确定）→ ② 地形离屏缓存（节点数降两个数量级）→ ③ 相机抽 `core/camera.js` → ④ 其余别动。
5. **一句话立场**：这套工具的瓶颈在**数据规模**和**撤销粒度**，不在"代码重复"。先解决会让你卡的地方。

**横切重复面**（三套各写一份，语义几乎相同）：

| 能力 | 对局地图 | 领地 | 大地图 | 差异 |
| --- | --- | --- | --- | --- |
| 相机 zoom/pan | `zoom` 0.4~6 + `panX/panY`（viewBox） | `zoom` 0.5~4 + `viewX/viewY`（viewBox） | `zoom` 30~220 + 容器 scroll | 🔴 语义/机制都不同 |

## 2. 架构提案（带迁移路径，不是一次性重写）

```
tools/map-editor/
├── core/                    # 零 DOM、可单测
│   ├── hex-grid.js          # ✅ 已有：几何唯一口径
│   ├── history.js           # 【新】泛型 op-log 撤销栈
│   ├── hit-test.js          # 【新】cellId ⇄ 坐标反算（把三套的 cellAtLocal 收进来）
│   └── validate-runner.js   # 【新】规则数组 → issues（增量重算受影响格）
├── render/
│   ├── terrain-cache.js     # 【新】地形层离屏缓存（一次性绘制 → 一张位图）
│   └── svg-view.js          # 现有 SVG 渲染调度（chunk / 层 / 只重画变化格）
├── editors/
│   ├── board.js             # 对局地图：只提供 config + 校验 + 序列化
│   ├── territory.js
│   └── bigmap.js
└── formats/                 # ✅ 已有：数据格式与校验
```

**每个 editor 只剩三件事**：
```js
export const config = {
  cells: { resolve: (map, hexId) => ({ terrainClass, entityKind, entityId }) },
  tools: [{ id: 'brush', paint: (ctx, hexId) => ops }],
  validate: (map) => issues,
  serialize: (model) => payload,
};
```
理想状态下每套 300~400 行（现在 1000~3000），但**这是第三步才做的事**。

### 迁移三步（每步都能独立上线 + 独立验证）

| 步 | 内容 | 影响面 | 判据 |
| --- | --- | --- | --- |
| ① 撤销改 op-log | 三套各自换 `history.js`，先只换大地图 | 单文件 | 同一组操作，undo 后 JSON 与旧实现逐字节一致 |
| ② 地形离屏缓存 | 大地图先上（格数最多） | 单文件 | 首次渲染后 DOM 节点数 < 800；编辑一格的重绘 < 8ms |
| ③ 抽 hit-test + 相机 | 把 `cellAtLocal` 收进 core；相机保持各自实现 | 三套各 30 行 | 三套 `hitAt(x,y)` 探针结果一致 |

**不建议一步到位**：三套都在用，一次重写意味着三套同时回归，出问题分不清是新内核还是原逻辑。

## 3. 四个关键决策

### 3.1 渲染：SVG 还是 Canvas？→ **分档，且先做离屏缓存**

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| A. 纯 SVG（现状） | ≤ 2000 格 | 交互免费（hover/事件/命中），节点多了掉帧 |
| **B. SVG + 地形离屏位图（推荐）** | 2000 ~ 20000 格 | 改 60 行：地形画到 `OffscreenCanvas` → `toDataURL` → 当 `<image>` 垫底，SVG 只保留**被编辑过的格 + 实体** |
| C. 纯 Canvas 2D | > 20000 格 | 命中/hover/文本全要自己实现，等于重写渲染层 |

**推荐 B**。理由：它把"10000 个 path"压成"1 张图 + 几百个节点"，但**不用重写交互**。
判据：`document.querySelectorAll('#board path').length < 800` 即达标。

> C 只有在"格子 > 2 万"或"要实时动画"时才值。现在 100×100 用 B 就够了。

### 3.2 撤销：全量快照 → **op-log**

现状：`snapshot() = JSON.parse(JSON.stringify(map))`，每步一份完整地图。40×40 的布局 11.7KB（60 步 ≈ 700KB，还好）；
100×100 + 74 座城会到 60~100KB/份（60 步 4~6MB），且每次 commit 都有一次深拷贝 + 序列化。

改成操作日志：
```js
// 一条 op 平均 100~200 字节
{ op: 'setTerrain', hexId: 1234, from: 'plain', to: 'water' }
{ op: 'addCity', cityId: 101, payload: { anchorHexId, hexIds, ring } }   // payload 供 undo
{ op: 'removeCity', cityId: 101, payload: {...} }
{ op: 'batch', ops: [...] }                                             // 一次拖拽 = 一条 batch
```
- `undo = 反向执行`；`redo = 正向执行`
- 内存：6MB → 几十 KB
- 顺带解决**撤销粒度**：现在"一次拖拽"靠 `endStroke` 手动合并，op-log 天然按 `batch` 合并

**风险**：每种编辑都要写正/反两个 op，漏一个就是"撤销不干净"。判据必须硬：
**同一组操作跑完 → 全部 undo → `JSON.stringify(map)` 与操作前逐字节相等**。

### 3.3 校验：点按钮 → **双轨（即时 lint + 发布权威）**

现状：点「校验」才跑，红环才出现；编辑时不知道有没有引入问题。

| 层 | 时机 | 规则 | 用途 |
| --- | --- | --- | --- |
| 即时 lint | 每次 op 后，**只重算受影响格及其邻居** | 重叠 / 越界 / 连通性 | 红环跟着编辑走 |
| 权威校验 | 保存 / 发布时全量 | 完整规则（含跨表对账） | 挡住脏数据 |

**不要**把全量校验塞进每帧 —— 现在领地一次全量校验 ~10ms，100×100 会到 100ms 级。
增量重算的边界：`op` 涉及的格 + 1 环邻居（连通性判定只需要局部）。

### 3.4 数据契约：统一中间表示，但**只在内核层用**

三套产物格式不同（对局是 `ascii` 字符画 + 站点数组，领地是 footprint 列表，大地图是布局 JSON）。不要强行统一产物 —— 那会牵动客户端与转表链路。

只在编辑器内核里用一层中间表示：
```ts
interface EditorModel {
  grid: { rows, columns };
  cellProps: Map<hexId, Record<string, unknown>>;   // 地形/分区/候选…
  entities: Entity[];                                // 城/怪/站点/装饰，统一带 footprint
}
```
`serialize()` 负责转回各自格式。**收益**：内核、命中、撤销、框选全部只认这一层。

## 4. 体验优化（按 ROI 排序）

| # | 优化 | 现在 | 为什么值得 | 量级 |
| --- | --- | --- | --- | --- |
| 1 | **撤销粒度对齐直觉** | 拖一笔 = 一步（靠 `endStroke` 手动合并） | 现在"刷了 30 格再撤销"会一次全退，没法精确回退一步 | 小（op-log 自带） |
| 2 | **框选 + 批量** | 只能单格点 / 笔刷刷 | 领地把 20 个候选格改成站点，现在要刷 20 次 | 中 |
| 3 | **实时校验红环** | 点「校验」才出 | 画完 100 格才发现重叠，白干 | 中（见 §3.3） |
| 4 | **图层显隐统一** | 只有大地图有 4 个开关 | 大地图能关范围/区块/编号，另两套没有；反过来领地需要"只显示某类站点" | 小 |
| 5 | **悬停就近信息** | 只有坐标 | 领地悬停显示"这个格子属于哪个战斗 id、能放几个基地"，比点开面板快 | 小 |
| 6 | **变更摘要（导出 diff）** | 无 | 策划改完图给程序看差异，现在只能 git diff 大 JSON | 小（同 op-log） |

**不建议做的体验项**：命令面板（Ctrl+K）、主题切换、拖拽排序面板 —— 这些是"看起来高级"，对这三个工具的实际操作频率没有帮助。

## 5. 什么时候才值得动

| 触发条件 | 该做什么 |
| --- | --- |
| 大地图要上真的 100×100 布局（现在只有 40×40） | 先做 §3.1-B 离屏缓存 + §3.2 op-log |
| 新增第四套编辑器 | 才值得抽 `core/history` + `core/hit-test`（省 400 行 × 复制度） |
| 单次编辑到 `render` > 16ms（一帧） | 立刻上离屏缓存，不要先优化算法 |
| 策划反馈"撤销不听话" | 上 op-log |

**没到这些条件就继续用现在的结构**。三套都在稳定产出图，为了"架构好看"重写是最差的投入。

## 6. 风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 🔴 共享内核变上帝对象 | 三套差异一旦塞进 `if (kind === 'bigmap')`，内核就废了 | 内核只提供**机制**（相机/历史/命中），**策略**（怎么画、怎么校验）全部留在 editor |
| 🔴 三套同时回归 | 一起改就分不清是谁的问题 | 严格按 §2 三步走，每步单独验证 + 探针留档 |
| op-log 漏反操作 | "撤销不干净"是最难查的 bug | 硬判据：全 undo 后 JSON 逐字节相等（三套各一条测试） |
| 离屏缓存与编辑不同步 | 缓存图脏了，画面就错 | 只缓存"未被编辑过的地形"；编辑过的格永远走 SVG 覆盖层 |
| 对局地图是 IIFE | 抽共享代码抽不到它 | 要么接受它独立（现状），要么单独一次改成 module（风险自担） |

---

## 7. 一句话总结

**这套工具现在缺的不是"更漂亮的架构"，是"在大图上不卡"和"撤销听话"。**
先把这两件做掉（约 150 行改动，可独立验证），再谈抽内核；
真要抽内核，也只抽那 400 行横切件 —— 剩下的 5000 行是三个不同产品，统一它们是负收益。
